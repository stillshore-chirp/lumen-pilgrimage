依存関係は [README の起動手順](../README.md#起動と操作) に沿って用意します。変更時に必要な共通ゲートは [AGENTS.md](../AGENTS.md#検証)、文書変更の受け入れ条件は [文書の責務と更新基準](documentation-structure.md#更新と受け入れ) を参照してください。

## 制作前の検証設計

調査・設計・制作実装・検証の共通工程は[専門分野の業務工程](agent-harness.md#専門分野の業務工程)、合否と証拠の原則は[受け入れと実物検証](agent-harness.md#受け入れと実物検証)に従います。制作前に、依頼と設計の正本から受け入れ条件を定め、各条件について次の確認方法を設計資料またはIssueへ記録します。全関連分野の確認を、単体の生成・構造、配置・組合せ・伝達、知覚・体験と、分野間の相互作用へ対応付けます。

| 記録項目 | 確認する内容 |
| --- | --- |
| 受け入れ条件と判定基準 | どの用途・要件を満たすか、合否を分ける観察結果・測定値・許容範囲、依頼内で必須か任意か。数値だけで表せない品質には、比較対象と観察する差を示します。 |
| 入力と条件 | 使用する素材・データ・版、初期状態、位置・向き・画角、時刻、移動経路、音量、描画設定、操作手順など、結果に影響する条件。 |
| 機器と環境 | OS、ブラウザー、画面・音響・入力機器と設定、必要な較正、模擬した部分、実機を使う場合の機種と接続方法。 |
| 観察・測定方法 | 見る・聴く・操作する対象、測定する量と方法、比較条件、保存する画像・音声・ログとその参照先。 |
| 結果と制約 | 実施日時と対象版、期待結果と実結果、合否、その方法で確認できた範囲、未実施・未確認の必須条件と解消方法。 |

見た目、定位、材質感、空間のつながり、操作感などの知覚要求は、成果物を観察・試聴・操作し、必要な測定を組み合わせて直接評価します。設計した数値が入っていることや画像の画素差だけで、要求した体験を合格にしません。下記の既存ゲートが受け入れ条件を拾えない場合は、対象に近い検証や利用条件をそろえた直接評価を追加します。

## 証拠の範囲と確認できない条件

証拠には、次の種類と確認範囲を併記します。直接観察した結果と、資料・計算からの推定を区別し、各手法で示せない部分は[受け入れと実物検証](agent-harness.md#受け入れと実物検証)の原則に従って扱います。

| 証拠の種類 | このリポジトリでの例 | 別に確認が必要な範囲 |
| --- | --- | --- |
| 計算・シミュレーション | 形状の余裕、音の経路・残響の計算。 | モデルや仮定の適用条件、制作物・出力での成立。 |
| 模擬入力・模擬メディア | WebXR、共有ダイアログ、合成映像・音声を用いるブラウザー試験。 | 実コントローラーの操作・追跡、OSの画面取得・音声経路。 |
| ブラウザー出力の測定 | 描画の画素値、Web Audioの波形・遅延。 | 表示機器やレンズを通した見え方、耳元での定位・聴感。 |
| 実機測定 | 使用機器と条件を記録したフレーム時間、表示・音響・入力の測定。 | 測定していない機種・環境への一般化、測定量に含まれない知覚品質。 |
| 知覚評価 | 条件をそろえた観察・試聴・操作と、評価者の所見。 | 評価していない経路・条件、別の利用者の反応。利用者の反応を測った結果と所見を分けます。 |

開発側の必須検証で機器、データ、権限、観測手段を利用できず代替確認を行った場合は、結果に「代替方法・確認範囲・限界・未確認の必須条件・解消に必要な環境や操作」を併記します。たとえば合成音の伝送が通っても、OSの音声経路が受け入れに含まれるなら、その条件は未確認のまま保持します。独立して進められる工程を続け、阻害された工程の達成済み成果・残作業・解消条件はIssue・PRへ記録します。未実施を確認済みへ置き換えたり、結果に合わせて必須を任意へ変更したりせず、元の受け入れ条件と照合します。

所有者の対象機器で行う確認は、[実機確認と開発受け入れの分離](agent-harness.md#実機確認と開発受け入れの分離)に従います。下記の実機手順は運用確認用で、Issue受け入れ・Ready・マージ・closeの前提ではありません。開発環境で実行できる確認を終え、その証拠と実機の未確認を分けて記録します。

全体の判定・画面上の要約・レポートは、下位の必須ケース、演奏イベント、工程の不合格と未検証を引き継いでください。下位の測定結果を詳細JSONにだけ置き、上位では「不合格なし」と表示して合格を連想させてはいけません。`null`、測定窓の無音、対象不足、検査していない項目、空の検査集合を合格へ変換しません。上位の判定に反映する集約規則を設計し、不合格・欠測を含む実データで、保存値と利用者が読む要約の両方を検証します。

### 運用確認の記録と既存Issueの整理

受け入れ欄には実装・開発環境の描画/音/操作・模擬XR・計測・回帰・レビューと配送の条件を置きます。機器固有の判読性、姿勢、色、追跡、コントローラー、実音声、実GPUの性能は別の運用確認欄へ置き、未実施を開発進捗の分母へ数えません。通常画面や模擬XRで確認できる同じ機能まで省略しないでください。

既存の実機待ちは、関連PRがmainに入っているか、開発側の条件・回帰・レビューが完了したかを先に照合します。移す条件と理由・影響を記録し、旧条件を取り消し線等で追跡できるようにして運用手順へ参照します。開発側も配送済みならcloseできます。未merge・未実装・開発側の未検証/不合格はそのまま残し、必要な作業を終えてから判定します。

## ワールド制作の検証記録

適用と進行可否の正本は[初回提示の品質基準](agent-harness.md#ワールドの初回提示の品質基準)です。本節はその証拠の取得・比較・再検証の方法を定めます。対象の設計正本と検証記録を参照し、Issue・PRへ同じ内容を多重転記しません。対象版、確認者、日時、受け入れ条件IDと実結果を結び、未実施・不合格を上位の判定にも引き継ぎます。

### 観察・設計・出力を結ぶ記録

参考画像の原資料IDと版、解像度・縦横比・向き、取得と利用条件を[素材ガイド](assets.md#参考画像と解析用の派生物)へ対応付けます。全景、重複グリッドの範囲、対象別切り出しは原画像の画素座標（原点・軸・矩形範囲の規約を明記）で識別します。同一物体のID、特徴点・輪郭・支持/接続・遮蔽の関係、観察と推定の確度を設計正本で統合し、3Dの座標・寸法・生成定義へ結びます。切り出しの確認だけで全景の整合を省略しません。

設計記録では、世界の平面・断面と、許可する移動/姿勢、窓・開口・反射・遮蔽解除から決めた観察範囲を対応付けます。画像に対応する観察点と、画像外・構造・環境の成立を調べる観察点は別のIDにします。粗い3Dモデルの起動方法・入力版・実巡回結果・独立設計レビューと是正、詳細版の結果を同じ対象へ対応付け、重大な構造問題の解消前に詳細制作へ進んでいないことを確認します。

### 比較画像の取得条件

候補版と最終版では、全景と初期解析のグリッド・対象領域を再取得します。比較元・変更後の実行入力（commitに加え未回収の入力差分があればその同一性）、参照原本、撮影手順・ツール/版と次の値を保存します。

| 条件 | 記録・照合する値 |
| --- | --- |
| 表示と内部描画 | CSS viewport、出力画像の画素寸法、aspect、devicePixelRatio、実際のdrawing buffer幅/高さ、レンダー倍率・品質設定。CSS寸法から内部解像度を推測しません。 |
| カメラ | ワールド位置、方向/quaternion、眼高・姿勢、垂直FOV、zoom、aspect、near/far、projection/view matrixとview offsetの使用有無。XRは眼ごとの投影と模擬/実機の区分。 |
| 光・環境 | 時刻と経過時間、照明/露出/色処理、天候、雲/水/風/生物の状態、必要なseed、可視/LOD条件。制御していない変数は差として残します。 |
| 比較方法 | 全景の対応、原寸並列、同一座標のcrop、必要なoverlay・特徴点/輪郭/接点の誤差と許容値、観察結果。加工した画像は原出力との対応。 |

Three.jsでは[WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html)の `getDrawingBufferSize` と実際の出力を照合し、[PerspectiveCamera](https://threejs.org/docs/pages/PerspectiveCamera.html)の投影条件を取得します。使用中の版のAPIと実値を確認し、設定値の保存だけで出力一致を認定しません。写真の撮影条件は確認できた値と推定を分け、単眼画像で一意に復元できない深度・材質・寸法を仮定として残します。投影差・露出差・動く対象の差を、形状や材質の不良と区別して診断します。画素差や単一の類似度を完成品質の合否の代用にはしません。

### 全方向と連続経路の確認

[粗いモデル](agent-harness.md#粗い3dモデルと独立設計レビュー)、制作候補、最終版それぞれで、設計した範囲と経路に確認結果を対応付けます。開始点・写真方向・反対方向・左右・上下、座位/立位/低姿勢、主要動線・移動端・高低差・窓端・開口・遮蔽物の背後を対象に、重要点での360°観察と連続した移動を行います。許可する入力や頭部移動が増えた場合は観察範囲も更新します。

対象点・経路・視線/姿勢・環境状態ごとの被覆表から画像/動画・録音・操作・計測へ参照を置きます。固定点の画像だけでは、移動中に現れる欠落や出現/消失を確認済みにしません。有限個の視点を撮った数だけで連続領域全体を証明せず、共有座標・支持面・開口・水際・地形の接続という設計上の条件と、危険箇所を横切る経路の直接確認を組み合わせます。確認していない領域・状態は明示します。

幾何検査は、実メッシュと実カメラの投影、接地/支持・開口・重複面の検査を対象にします。[Raycaster](https://threejs.org/docs/pages/Raycaster.html)を使う場合は対象layer・子孫・表裏の扱いを記録します。別の代理形状だけに接点があることや、裏面を無視したrayの非交差を立体の成立証拠にしません。材・水・霞・影などを診断用に分離した結果は原因分析用とし、最終の通常表示でも再確認します。

昼夜、灯具の点消灯、天候・時間進行、音源/生物の状態、離脱/再訪など該当する変化について、切替中と安定後を確認します。構造の切断、支持や裏面の欠落、奥行きの不足、不自然な水際やLOD境界、状態の不連続が見つかった場合は、不合格の位置・入力・画像を保存します。形状・配置・材・光・投影・環境モデルへ原因を分け、設計起因なら正本・図面・共通データ・生成処理を直し、同じ失敗経路と変更の影響先で再判定します。

### 高さに応じた飛行の確認

`node --test scripts/coast-controls.test.mjs` は、純粋な上昇/下降、斜め移動、衝突時の最後に安全なXYZ、従来の2引数判定、床/天井、模擬head offsetと退避を確認します。亭は段違い屋根上の通過と主外殻内の停止、ドーム頂部および側面の余裕境界の内外を調べます。形状と移動の検査は、[ナビゲーション契約](worlds.md#共通座標ナビゲーション契約)と同じカメラ中心・余裕半径を使います。

ビルド後の直接確認では、`?world=overlook` を開き、通常の自由飛行で屋根の側面・下面・上方へ近づきます。屋根の実体で停止し、その上空を水平に通過できることを同じ姿勢と入力時間で比較します。上階西端x=10.88 mを越える上空経路と、純粋な上昇/下降、斜め接近を含め、cameraの時系列位置と主描画を保存します。代表的な比較起点は(x=29 m, y≈400.265 m, z=20 m)です。x=24 m付近は既存の上階平面内にあるため、その通過だけで旧平面境界の解消を判定しません。

模擬XRでは頭部を含む移動停止と重なりからの退避を調べ、1対1の物理head追跡を制限した結果へ読み替えません。実HMDの追跡や機器固有の見え方は所有者の運用確認として別記します。飛行修正の確認は、地形・植生・舗装・遠景・音響を含むワールド全域の完成判定を代替しません。

### 展望台の表示地形と局所支持

`node --test scripts/coast-terrain.test.mjs` は、地形のtile化前後で面・頂点・法線が保たれることと、`sampleHeight` が実Float32三角形への独立ray交差に一致することを確認します。格子の対角線の両側、格子/帯の境、表示field端と非有限入力を含めます。解析標高関数を同じ関数で再計算しただけの一致は、表示面の検査へ数えません。

配置全数を調べる場合は、実instance matrixで変換した幹下部/株元・岩の基部と、同座標の実表示triangleを照合します。葉先を基部の分母に含めず、地下根リングの離隔と目に見える幹の地表交差を区別します。基部の最高点が−10 mm以下（Float32誤差±0.1 mm）へ入ること、支持polygonが退化しないこと、全体埋没がないこと、個体数・局所形状・XZが意図せず変わらないことを合わせて記録します。

実画面は、同定したsage/buckwheatと緩斜面/急斜面の岩を、同じcamera・投影・内部buffer・時刻・品質で前後比較します。通常画角を主証拠にし、狭い診断画角やcropは補助へ分けます。目標位置に別の大きい株が重なる場合はactual world AABBと画面投影で対象を同定し、遠方の点が読めない画像を全個体の接触証明にしません。音源7点の支持高さと、無効な支持入力を音声graphの確保前に拒否することも確認します。

地形の入力が変われば、その入力と交差する個体/音源の支持を再検証します。全域や景観の合否、環境音の自然さ、実HMDの挙動はこの局所支持の判定と分けます。

### 展望台の床断面と受影

敷石は全fieldの厚み・閉鎖面・面向き・重複面と、bed/grout/既存capの接触を実geometryで照合します。非石部と外縁の旧高さ、亭の実6footprintのbearing、backingからcap/foundationまでの連続を確認し、敷居の抽出前後で亭の描画属性/indexと飛行volumeが変わらないことを比較します。歩行の基準Y=346 mと足音の材区分も保持します。

通常画角で床の全景、notch、敷居、rear外周を立位・低姿勢・許可された低い飛行から比較します。敷居前の例はcamera(0,346.30,7.45) m、target(0,345.985,8.565) mです。カメラ・投影・raster・時刻・品質を揃え、支持帯が前面へつながること、床の不意な段差や過度な目地の溝がないことを確認します。上面が床裏を遮る画像は、下面の支持証明へ使いません。

斜めの縞などが現れる場合は、map/bump無効とreceiveShadow無効を別々に比較し、材・geometry・受影の原因を分けます。診断後は元の状態へ復帰して通常frameとの一致を確認し、診断画像で品質合格を出しません。全影無効や支持寸法の変更で原因を隠さず、受影の是正は通常の光と接触影を残す条件で確認します。床支持と材/影の最終品質は別の判定です。

局所受影のCPU回帰も `node --test scripts/coast-terrain.test.mjs` に含めます。domainを実支持前面へ照合し、normalBias付き比較座標と実面のUVアンカーを混同したときの内外判定反転を、独立なUV連立式で再現します。生成shaderでunbiased UVの受け渡しと比較深度の分離を確認し、options未指定・非選択材の経路を照合します。これはGPU compileや完成画質の代替ではありません。

ブラウザーでは低眼高の敷居前、昼夜、左右の実端、通常のベンチ・手すり、固定方向の小移動を確認します。対象前面の縞だけでなく、別casterの接触影、支持面と周辺との境界、domainに有効texelがない場合の切替を観察します。少数の静止点は、その間のすべての頭部移動や連続境界を証明しません。材の斑と影の細筋を区別し、原因を再分離していない残留模様は観察結果のまま記録します。

深度を診断する場合は、通常frameの描画直後に取得したactual shadow matrix、map寸法、比較方式と現在の受影点からkernel texelを求めます。別frameのindexを流用しません。比較samplerの逆算には、実textureのtype/format/filter/compare、実uniform binding、比較深度0/1と既知depth control、kernelの被覆、原map不変、診断資源の解放と通常PNG hashの復帰を対応付けます。depth=1は正当なclear領域の場合があり、全binaryという条件だけで正しい取得としません。比較samplerの逆算、raw attachment取得、実fragment導関数の取得は区別します。source/distと実画面・数値の版付き証拠はIssue/PRの検証記録から参照し、実GPU費用と未確認の物理HMD条件も別記します。

2026-11-28の固定候補比較では、ANGLE/Metal・1920×1080・DPR1・high/day、同じcameraと姿勢で各24有効queryを取得しました。展望台はprepareRenderを持たないためmain描画だけを測り、受影補正前C9の中央値5.174 msに対し有限面v2入りC11Rは5.337 ms（約3.16%増）でした。disjoint、未取得query、計測中のprogram増加は0です。単回・固定順・短時間の局所費用であり、全域の平均や実HMDの達成保証ではありません。

### 展望台の道路地形と道路音

設計入力と生成順は [道路と地形の設計](overlook/road-terrain-design.md) を正本とします。`node --test scripts/coast-terrain.test.mjs` で元16路のXZ/横断frame、縦断の小さい持上げ、実chordの勾配、近側の地中曲線、実地面の切断と合成sampler、実headwallの開孔、背面の土断面と車両matrixの有限性を確認します。幅とshared XYZ、車両包絡、slabの閉鎖は共通planと生成geometryを別途照合します。独立した全数検査では、lining外三角形と掘削前地表の交差polygon全体で土被りを調べ、橋脚の全footprintと実地盤・slabを照合します。頂点だけのsampleや公称中心の重なりを全域の最小離隔へ読み替えません。

道路の支持volumeと描画面の所有も分けて確認します。閉鎖slab全三角形のedge閉鎖、実asphaltとの上面一致、下面と両端面の保持、内部上面・側面の非描画、道路あたり一つの可視groupと資源解放をterrain testで調べます。遠方の通常像に破片や筋が出た場合は、実camera/projectionと深度bufferの精度を記録し、同一状態の一時表示切替で原因を分離します。診断の非表示像を採用品質とせず、修正後は正常な全外殻を描いて昼夜・斜め・下面・端面・隣接物の遮蔽を比較します。

実画面では主床の同cameraの昼夜・左右・背面と、高さ450 mの全周を比較します。旧切断の比較点はcamera(33,450付近,−22.5) mの東向き見下ろしです。坑口は実ID、入口・上/下・側面、車/灯火の通過を対応付け、手前地形に遮られた像と口内の確認を分けます。遠方13端は通常画角の実投影・遮蔽・原寸可読性で分類し、必要な端だけ追加観察します。外部XZや通常到達しないYを使う診断は、合法経路の実証と別記します。移動範囲や霞を変えて可視境界を隠すことは受け入れません。

道路音では源長の分割総和、左右孔のarrival、manualの内外距離、Panner rolloff=0、元8路の再生率/offset、非有限metadataのgraph生成前拒否をCPUで確認します。実PCMは同じ音源buffer・開始位相・seed・mix・cameraで旧8声と新22声を各30秒、正規化なしのlossless LRへ収録します。mono/LRの20–125 Hzと125 Hz–4 kHzの帯域RMS、1秒envelope、peak、声間相関を比較し、源powerと耳元の合算を同一視しません。固定yawと左右90°は区間を分け、聴感では定位の飛び、反復・位相のうなり、音量・高域の不自然な変化を調べます。

CPU/GCとHRTF負荷は録音器を外した実ブラウザーで、同じpose・画質・warm-up・区間を使って測ります。Nodeの伝搬計算時間だけを音声graphやGPU/HMD性能へ読み替えません。音声の採用素材は変えず、坑内反射・放射指向性の測定モデルを実装したとは報告しません。実HMDの確認は所有者の運用記録へ分けます。

### 最適化と実行性能

空間構造の検査と、LOD・カリング・チャンク/読込み・更新頻度の選択の検査を分けます。正面だけでなく、境界横断、急な向き変更、接近/離脱、影・反射に見える対象、再訪の経路で確認します。遠方という分類だけで板状化や未完成面を許容せず、利用距離・視角・移動速度・重要性から選んだ簡略化の結果を直接比較します。音・生物・環境の状態も同じ世界の時間と位置へ整合することを確認します。

性能要件がある場合は、機器・OS/ブラウザー・解像度/DPR・画質・状態・経路、ウォームアップと計測区間を定め、GPU/CPUフレーム時間、メモリ、初期化/更新コストなど必要な量と判定基準を記録します。GPU時間の測定ができない場合は未測定とし、draw callや三角形数、ソフトウェア描画や模擬XRの値を実GPU/HMD性能と同一視しません。最適化で負荷が下がっても知覚品質の不合格は解消扱いにしません。

### ハーネスの机上適用検証

以下は本工程の適用を検討した5ケースです。各ケースの検出、証拠、不合格、戻し先、修正判定を規範と照合しました。結果はいずれも、指摘を未達として保持し必要な設計・実物確認へ戻す工程が接続されることです。これは実ワールドの描画・操作・音・性能を測った結果ではありません。将来の制作では各欄に対象版と実物の証拠が必要です。

#### ケースA：主視点と写真方向が異なる施設

- 検出：着手で開始位置と用途を確定し、全域設計と粗い3Dの主視点/反対方向を独立設計レビューへ出す。候補版でも同方向を観察する。
- 証拠：開始位置/向き・写真対応点の図とcamera値、用途/配置の設計、粗い3Dの正面/背面画像、レビュー指摘と是正の版。
- 不合格：写真方向が一致していても、開始視界に意図した用途・奥行きが成立しない。
- 差し戻し：全域のゾーニング、開始体験、視線/用途の設計正本と粗いモデル。
- 修正判定：同じ主視点と360°/移動経路で用途・接続を再評価し、独立設計レビューの重大指摘を閉じてから詳細制作。最終版でも再確認。

#### ケースB：窓端で現れる水際の切断

- 検出：観察包絡の設計、粗い3Dの両窓端/低姿勢、窓へ寄る連続移動と斜めの視線。
- 証拠：岸/水/斜面の共通座標、端部の経路と眼高・視線、切断が現れる画像/動画、支持/接続の実メッシュ検査。
- 不合格：岸と斜面の終端、隙間や制作境界が許可された位置/姿勢から露出する。
- 差し戻し：全域の地形・湖岸・水面の連続、移動/観察境界の設計。視界を隠すだけの修正で必要範囲を削らない。
- 修正判定：失敗位置と両端を横切る同条件経路、通常の水/材/霞の状態で切断が消え、支持・接続と周辺の見通しが成立することを確認。

#### ケースC：建築の裏面と開口の欠落

- 検出：全域の平面/断面と支持構造のレビュー、粗い3Dの背面・見上げ・見下ろし・開口の奥・反射面。
- 証拠：建築の閉鎖面/支持/隣接空間の図、対象IDと実形状、表裏を区別したray/接触検査、各視点の実出力。
- 不合格：輪郭が一致しても、見える背面/床裏/屋根裏が欠ける、支持がない、開口の先の空間が成立しない。
- 差し戻し：建築の全体形状・床/屋根・支持・開口/隣接空間の設計と生成定義。
- 修正判定：同じ視点/姿勢と開口沿いの移動、影/反射を含む通常出力で再確認し、図と実形状・移動支持面の一致を照合。

#### ケースD：移動や時間で崩れる環境

- 検出：設計で地勢・植生・生物・光/音の位置と状態を照合し、候補/最終版の連続巡回、時間/天候・LOD・再訪を評価。
- 証拠：共通座標/状態と時間の定義、経路・切替時刻・seed・品質、動画/録音・負荷測定、出現/消失と伝搬の比較結果。
- 不合格：遠景や植生が不自然に消える、音や生物が地形に整合しない、切替・再訪で環境の関係が不連続になる。
- 差し戻し：地形/生態/音/照明の環境モデル、状態寿命と最適化の選択設計。
- 修正判定：同経路と状態遷移、近接/離脱/反射/再訪を再実行し、連続性・実出力品質と該当性能要件の両方を確認。

#### ケースE：設計対象が実視界では遮蔽される

- 検出：原画像の遮蔽関係を再統合し、粗い3Dの主視点と候補版の全体/対象cropを独立評価。
- 証拠：対象ID・特徴点・可視領域の設計、実カメラの投影と遮蔽メッシュ、原寸の対応画像、独立レビューの判定。
- 不合格：解析・図面がそろっていても、体験に必要な対象や用途が開始点/必要な動線から読み取れない。
- 差し戻し：配置・高さ・開口・主視線と用途の設計。必要に応じ観察時の前後関係も再解釈する。
- 修正判定：同一camera/環境で全景と対象領域を比較し、連続経路で見通し・用途・周囲との接続を直接評価。座標テスト成功のみで通さない。

形式検査が確認するのは、[検査実装](../scripts/validate-harness.mjs)に定義した入口・正本見出し・様式の参照契約とリンクです。A〜Eの不合格の認識、専門判断、実物の確認や修正完了は、設計/コード/品質レビューと対象版の検証証拠で判定します。形式上の成功を、それらの実施や合格の証明にはしません。

## ゲートの選び方

外部音声を採用・加工する変更では、[音声の採用基準](assets.md#外部音声の採用基準)と個別案件の条件を照合し、`npm run validate:audio-samples` で台帳・配布ファイルのhash/bytes・使用パスを確認します。候補と採用済みを区別し、今回の箏に対するCC0限定を他案件の一律禁止へ広げません。この検査は権利連鎖・倫理・聴感の妥当性を保証せず、原典・切出し内容・品質の実質レビューが必要です。元録音を保持できない場合も、実際に取得した原本の種類・完全性・hashと取得手順を記録し、別の音声を同じ原本と扱いません。

| 変更範囲 | 実行するゲート | 確認できること |
| --- | --- | --- |
| 文書と参照だけ | `npm run validate:harness` | 現行文書と素材クレジットのリポジトリ内リンク、記載した npm スクリプト名、README からの到達可能性と、ワールド工程の正本見出し・入口/様式の参照契約を検査します。内容の正確さ、工程の実施、実画面品質や実機での動作は証明しません。 |
| アプリのコード | `npm run check:affected` | 比較元と変更入力から型/build・文書/素材・該当機能のNode試験を選びます。CIも同じ選択器を使います。 |
| 探索、移動、描画、音響、ワールド遷移 | `npm run check:affected -- --browser` | ビルドしたアプリの操作・描画・音響・時間帯引き継ぎをブラウザーで確認します。 |
| 仮想モニター、WebXR | `npm run check:affected -- --browser` | 別タブの接続、合成メディアの伝送、表示・配置・音声、Fキーでの掴みと解放、模擬WebXRでの探索を確認します。OSの画面選択ダイアログは試験用に置き換えます。 |
| 住戸または映画館 | `npm run check:affected -- --browser`（個別は residence/cinema のbrowser） | 該当ワールドの画面操作とブラウザー描画を確認します。物理ディスプレイ、スピーカー、VR機器の出力品質は所有者の運用確認へ分けます。 |
| 商業アトリウム | `npm run check:affected -- --browser`（個別は `test:atrium:browser`） | ソファ初期位置、立ち上がり、上階への移動、点灯による画面の変化を確認します。 |
| 湖畔の広間 | `npm run check:affected -- --browser`（個別は `test:lake:browser`） | 正面の昼夜、Fキーと模擬WebXRのグリップによる行灯と光源の持ち運び、両窓と背面の歩行境界、全方向の見え方、ワールド間の時刻、環境音と模擬WebXRを確認します。 |

`npm run check:affected` は通常のローカルとCIの選択ゲートです。ブラウザー試験と実機の画面共有・入力・音響は、それぞれ別の確認です。`validate:harness` は維持対象の各文書を README から辿れることも検査します。

## 変更影響によるゲート選択

通常の検証と全検査は目的を分けます。変更のないワールドの試験を、別のワールドを改修したというだけで実行しません。[選択器](../scripts/ci-impact.mjs)は単体試験・ブラウザーのconsumerから静的import、型依存、literal URLやsource読込みを追い、比較元の旧版と実際の実行treeの依存を合わせます。PRのmergeによってmain側に増えたconsumerも含め、topic headだけのgraphへ限定しません。JSON内の音声入力hash、生成bank/WAV、配布音源、共通音声素材などimportに現れない入力は、理由付きの宣言で補います。単なるディレクトリ名だけを影響判定に使いません。ブラウザーsuiteの名前だけで対象を決めず、海岸試験の住戸/映画館の足音、モニター試験の住戸照明・Quest操作など、そのsuiteが実際に開いて検証するsceneもconsumerとして保持します。

```sh
# origin/mainとの分岐点からHEAD、staged/unstagedとuntrackedを含める。
npm run check:affected

# 選択だけを確認し、検査は実行しない。
npm run check:affected -- --plan-only

# 必要なブラウザーゲートも実行。必要時だけbuildを補う。
npm run check:affected -- --browser

# 任意の確定版と比較する例（BASE_SHAを実際のcommitへ置き換える）。
npm run check:affected -- --base BASE_SHA --head HEAD
```

同じHEADで一度通した関連gateは、比較元、入力path・素材・設定・環境の閉包が変わらなければ再利用できます。merge後のclean mainで空差分になった計画を、以前の変更の検証結果に使いません。確定版との再検証には `--base` / `--head` を明示します。全検査を明示する場合は下の `npm run check` を使います。

| 入力の例 | 選択する範囲・扱い |
| --- | --- |
| 箏のオフライン物理モデルだけ | 共通の型/buildと箏の数値・音源入力の検査。変更していない他ワールドやbrowserは選ばない |
| 同梱箏WAV・音声bank・権利台帳 | 実ファイル/台帳/音源の整合、必要な湖畔・比較画面consumer。WAVの実出力をmock fetchだけで合格にしない |
| 共通の音声出力・操作/XR | その入力に依存する複数ワールド/モニターを選ぶ。共有入力の変更である根拠を残す |
| 文書だけ、リンク先の削除/改名 | harness。文書の本文が変わらなくても消失する参照先を検査。アプリやbrowserの合格とは記録しない |
| オフライン図面の生成・改訂入力 | `scripts/draw-cinema-speaker-mounts.mjs`、`scripts/revise-residence-drawings.py`、`docs/residence/source/residence-70f-revisions.json` はharness。再生成一致・可読性・実装との整合は各図面の手順で別に確認する |
| 同梱ソフトウェア通知 | `scripts/prepare-cinema-code-licenses.mjs` と既知のThree.js 0.184.0通知3ファイルはbuildとharness。実import/URL・試験consumerも加算し、同梱後の通知・記録の版/バイト/hashを別途照合する |
| build/依存/CIの設定、未知の実行入力、履歴不足、構文解析不能 | 理由付きの全標準gate。browser計画も保持し、未実行を合格にしない |

図面と通知の宣言は[選択器](../scripts/ci-impact.mjs)のexact pathに限定します。未登録の生成処理・改訂JSON・別版通知は理由付き全検査です。選択やgate成功だけで、再生成一致や権利条件への適合を保証しません。

[実行器](../scripts/check-affected.mjs)は固定したコマンド配列をshellなしで実行します。選択ゼロでは子processを起動せず、未選択を「非対象」、選択したが未実行のものを「未検証」とします。先行gateが失敗すると以後を止め、非ゼロ終了・signal・起動失敗・例外はCIの失敗です。成功した検査数で失敗を上書きしません。

`artifacts/ci/plan.json` に比較元/対象版・変更path・選択/非対象・理由、`results.json` に実結果、`summary.md` とgate別logへ証跡を残します。CIは同じ内容をStep Summaryと14日保存の `affected-validation` artifactへ出します。実機・知覚品質は、この選択結果で確認済みにしません。

### GitHubでの比較と必須チェック

[GitHubのPRイベント](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request)では、既定checkoutはmerge treeです。選択はイベントのbase SHAとtopic head SHAの分岐点からの差分、実行はcheckoutしたmerge treeとし、両者を記録します。main pushは[push payload](https://docs.github.com/en/webhooks/webhook-events-and-payloads#push)のbeforeからafterを直接比較します。可変のorigin/mainや固定HEADの親で代用しません。[Gitのmerge-base](https://git-scm.com/docs/git-merge-base)と[差分仕様](https://git-scm.com/docs/git-diff)に従い、削除/改名の旧新pathとNUL区切りを扱います。初期pushのzero SHAや不足履歴を空の成功へ変えません。checkoutは全履歴を取得します。

[必須チェックのskip仕様](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks#handling-skipped-but-required-checks)に従い、workflow自体をpath filterで消さず、既存の `validate` jobを常時起動して内部でgateを選びます。CIは標準gateを実行し、browserは従来どおり別のローカル/対象環境の検証です。[upload-artifact v4](https://github.com/actions/upload-artifact/blob/v4/README.md#inputs)は結果の保存に限定し、[GitHub/寄稿者のMIT条件](https://github.com/actions/upload-artifact/blob/v4/LICENSE)を確認しました。Actionのソースをゲームへ同梱しません。

### 選択規則の保守とレビュー

新しいworld、試験、動的読込み、素材/生成物を追加・変更するときは、選択器のテスト一覧・consumer・非import入力の宣言も照合します。packageの実コマンドと試験一覧がずれた場合、未登録の新しい試験がある場合は計画を不合格にし、登録・修正するまで成功にしません。未知の実行入力や履歴不足は理由付きの全検査とし、非対象へ放置しません。未知入力の対応を追加するときは、必要gateを選ぶ正例と無関係gateを省く負例の両方を `npm run test:ci-impact` で確かめます。任意の動的ファイルアクセスを完全に静的証明する仕組みではありません。新しい必須受け入れ条件が既存gateにない場合は、該当する直接評価を追加します。

## ブラウザでの回帰テスト

ブラウザー試験は、`dist/` を Vite のプレビューサーバーから開くため、実行前に `npm run build` を完了させます。`COAST_CHROME_CHANNEL=chrome` はインストール済みの Chrome を選びます。Playwright 付属の Chromium を使う場合は、必要に応じて `npx playwright install chromium --no-shell` を一度実行します。各試験は Playwright で自動操作し、実機の入力機器や音響機器は使いません。インストール済み Chrome で描画や操作の待機がタイムアウトする場合は、Playwright が指定する Chromium でも条件をそろえて確認できます。

景観探索のブラウザテストはビルド後に MacBook の Google Chrome で `COAST_CHROME_CHANNEL=chrome npm run test:coast:browser` を実行します。Playwright の Chromium を使う場合は、次のコマンドで準備と実行ができます。

```sh
npx playwright install chromium --no-shell
npm run test:coast:browser
```

ブラウザテストは、海岸と丘陵展望台の描画・音響・移動と時間帯の引き継ぎを確認します。足音は住戸と映画館も含めた全4ワールドで、歩行時の Web Audio 出力、静止・飛行時の発音停止、環境音との独立したオン・オフ、0% での消音を確認します。展望台ではデッキ、外周の石畳、階段で使われる音も比較します。全体・種類別音量のワールド間の保持、コンテキスト中断からの再開、音量スライダーの視野角との整列と狭い画面での収まりも検証します。音の詳細を開いて375×740から667×375へ切り替え、全体音量のボタンがドック内に収まり、種類別音量をスクロールして操作できることも確認します。音声の開始待ちにオフへ切り替える操作、模擬した自動再生制限下の再開、模擬したBFCache復帰通知による音量とオン・オフの再適用も確認します。

### 住戸の境界と音の直接確認

設計寸法と近似の正本は[住戸設計](residence/residence-70f-design.md#編集と再検証の入口)です。次を同じ配布入力・実カメラ・時間帯・品質へ結び付け、各結果の対象を記録します。

1. 茶室は板・梁の下面で飛行が止まり、高い取次では元の高さを保つことを実操作で確認します。tracked headは拘束せず、上面・吊材・主天井貫通・上階スラブを見回します。バルコニーは描画の実三角形へrayを当て、室内から敷居・勾配・手すりへ歩行と低姿勢で往復し、眼高を引いた足元と床を比べます。
2. 無窓室の昼は同じ位置から「全戸閉・人工灯off」「正規操作で開戸・off」「全戸閉・on」を比較します。対象の戸板の実位置も記録します。表示画素の平均はalphaを除外し、露出を固定します。画素平均を照度と呼ばず、暗部の形と材、点灯差を実画像で判定します。
3. 音源を固定し、壁から24/12/6/1 cm、閉戸・複数戸の連鎖、開いた戸板の背後、同室L字の角や固定ガラスの両側を比較します。全経路区間の実壁/leaf交差、方向・帯域・幾何遅延を照合します。動的な順位交代、短時間の再交代、消滅、軽量/高品質切替では、dry/sendの全応答と入力履歴を保ち、実PCMのclock・欠測・初動・差分を調べます。
4. TV/浮遊モニターは代替MediaStreamから実providerへ接続し、同じcontext/source/stream/track/利用者音量の保持を確認します。単点と6chの2接続（14 IR/21 HRTF）と環境音7 IRを同居させ、個別音量0・全体mute・停止後のtail、world離脱時の全接続解放を記録します。制御JavaScript、作者Worklet、ネイティブ全graphの負荷を分けます。CDPのrenderCapacityは実装・単位を確認して生比率で保存し、低頻度標本を全callbackの最大負荷にしません。OfflineのHRTF初期化をRealtimeへ同一視しません。
5. 窓端の外皮は合法なbody位置と1:1 tracked leanを固定し、期待する棟面のpointを実眼行列へ投影します。外向きraymissだけで欠落とせず、枠の遮蔽、frustum、通常主描画のpixelを対にします。factoryのinstance番号は街区を詰める前後で変わるため、productionのprefixとdescriptor、実draw数・ID・face・hit位置を照合します。星などのPointsは不透明な外皮のfirst-hit判定から除き、打切り記録を不透明面なしと解釈しません。

開発測定では、初期shadowの型不一致、自己反射へのread/write、context復元時の旧世代6資源の削除をそれぞれ切り分け、修正版の対象状態で0を確認しました。これは対象版・状態の局所結果で、全描画の無警告や実機性能の保証ではありません。近接陰影の16段階分散は旧来の筋を減らす一方、細粒の斑の主観品質は数値誤差だけで合格にしません。

1920×1080でprepareRenderから最終主描画までを測ったC7→C11Rの中央値7.1539→7.1242 msは、各24 queryの全閉包による単回の短い比較です。AOだけの改善率・統計的な同等性・PCVRの期限を示しません。C11Rの同階外皮は、productionでfactory107へ街区prefix4944を加えた実5051へ帰属し、昼のstrip ray4本と実画像を照合しました。runtimeのinstance行列自体は未採取で、Float32行列の再構成はCPUの証拠です。夜の保存rayは星のPointsで打ち切られたため、夜の不透明first-hit同定は未確認として残します。原寸画像の見え、通常の窓・BL・玄関C1、移動結果は別に記録します。

「メニュー」から「住戸の遠隔操作」を開き、照明・カーテン・家電と水栓の切り替えで外枠の寸法と位置がそろうことを、通常の画面、幅の狭い画面、幅と高さの小さい画面で確認します。高さの小さい画面では、選択中の一覧を末尾までスクロールしたときに最後の設備とカテゴリボタン、「閉じる」が画面に残ることを確認します。キーボードで一覧末尾の設備を開く操作、一覧に戻ったときのフォーカス、非選択の設備一覧が操作対象から外れることも確認します。

夜の南窓と東窓では、同じ画角で少しずつ視点を振ります。軽量・高品質の両方で街の画素の急な明暗変動を計測し、窓明かりが見える輝度も確認します。

仮想モニターの通し試験はビルド後に `COAST_CHROME_CHANNEL=chrome npm run test:monitor:browser` で実行します。別のブラウザコンテキスト間のWebRTC接続、承認、映像面の描画、音声波形、音量と描画品質の独立性、配置操作、停止と解放を検証します。ワールド間移動では、住戸のテレビと映画館スクリーンからの浮遊表示への切り替え、履歴移動、読み込み失敗・競合、同じ WebRTC 接続とメディアでの再生継続を検証します。WebXR セッションを模擬し、4ワールドで両眼の位置と追跡を確かめ、Touch の移動・旋回・飛行・近接操作・メニューによる移動、および VR 終了後の通常描画への復帰を確認します。描画パターンと合成音からブラウザーのメディアトラックを生成し、テスト側で `getDisplayMedia()` の画面選択を差し替えます。OSの実画面取得やシステム音声経路はこの試験の対象外です。`npm run test:monitor` のWebXR入力試験も模擬セッションで実行します。

共有音声の位置を調べるobserverは、作成・接続されたPannerの一覧と、現在の入力枝から到達しdry/mode gainが有効な経路を別に記録します。住戸providerは無音の経路slotも保持するため、一覧の先頭を物理音源とみなしません。既知の見通し条件では、寄与可能な到来経路の中にTVの物理位置とHRTFが含まれることを、実stream・context・mode・master・出力peakと合わせて確認します。surroundはsplitterの6出力ごとの経路帰属を保ちます。このgain判定は各入力chのPCM非ゼロを測るものではありません。従来の列挙値は残し、停止・切替・解放の検査を隠さないようにします。

再現調査では、元の試験module URL・作業ディレクトリ・ブラウザーchannelを保持し、版と条件を記録します。既定のChromiumと明示したChromeの結果は区別し、別の起動構成で対象場面へ到達できなかった診断を、元の機能不具合の再現として扱いません。

住戸の仮想モニターでは、テレビと浮遊表示の両方で、遠隔操作パネルと現地スイッチからリビング・ダイニングの照明を一括で切り替えます。パネルの開閉、映像面の非表示と再表示、時間帯・描画品質の変更、模擬した BFCache の保持・復帰通知を通じて、元の WebRTC 接続、受信ストリームとトラック、映像フレーム、音声波形が続くことを確認します。別の試験で配信側と視聴側の poll に一時障害を起こし、接続の維持、共有停止、再ペアリング、切断時の解放を確認します。BFCache の試験は保持・復帰通知を模擬します。実際にブラウザーがページをキャッシュする条件は端末とブラウザーに依存します。

配信音声の出力先は、サーバーが設定を反映した直後に応答だけを失わせて確認します。配信側のトラックの送出を先に切り替え、反映中に選んだ最新の設定が視聴側へ届くまで同じ接続で映像が続くことを確認します。設定の再送を待っている間に共有を停止できることも検証します。単体試験では、遅れて届いた旧音声設定が反映済みの値と生存確認の期限を更新しないことを確認します。模擬時計でシグナリング停止中の同一接続での復帰と、承認または生存確認の期限に達したときのメディア解放を確認します。

### 映画館の機器接続と接近

[筐体と取付の現行設計](cinema/cinema-speaker-mounts.md)を基準に、全48台の放射面と音響中心・向き、支持材両端と取付板、屋根・壁への接続を配置試験で照合します。実メッシュの詳細が共通の接触箱内にあることと、丸みで生じる保守的な差も確認します。

実画面では清掃モードで、天井機器を横からと上から、後壁機器を壁沿いの斜めから観察します。同じ位置・quaternion・projection・描画解像度・画質・照明で比較し、筐体、背面板、2本の支持材、屋根・壁側の取付座まで接続が読めることを確認します。

[還気口](cinema/cinema-ventilation.md)は4か所の下面・斜めと、元のコファー下面を貫通する実空隙を確認します。口の下から正規飛行で上昇・保持・逆向き退避し、有限の実姿勢と最終clear判定を保存します。静止頭部追跡から見た内面は別に記録します。環境音は同ループ位相・音量・頭部で前後の距離、帯域レベル、左右差とオン・オフ、退出再訪を比較します。対象版ごとの実施範囲は[再評価の検証記録](cinema/cinema-reevaluation-verification.md)に記します。

通常の移動入力では下・横・上・斜めと垂直だけの飛行を試し、模擬XRでは頭部offsetを加えた実際の頭部中心で移動が止まること、重なった位置から安全な向きへ退避できることを確かめます。一方、静止中の追跡された頭部の1:1移動は衝突で遮断しません。その頭部移動で見える閉じた筐体、上面、裏面、取付の奥も可視包絡に含め、隠れた面の欠落や接続の破綻を確認します。locomotionの停止と静止中の頭部追跡を別に記録します。全台の共通定義・実メッシュ検査と危険箇所の連続経路を組み合わせ、少数の写真だけで全台を合格にしません。


最終の連続巡回では、R09からR01、左縦通路、R08・R15の車いす位置、後方横通路、右縦通路、R09へ戻ります。座位・立位・低姿勢と回頭を同じ連続経路で記録し、別poseへ移した写真と区別します。幕端、コファー、左右の映写窓の実開口中心、上部機器を含めます。共有映像は実受信寸法とtrack状態、2.39・左右部分白・白・黒8秒・復帰を記録します。再訪時は既存のarrival/auto初期化と、その後の通常UI設定・表示を確認します。worldを越えた照明設定の永続化を仮定しません。

幕の裏は、bodyを`z=0.65m`に置いてから模擬XRを開始し、静止headを`z=-1m`へ動かします。要求値だけでなく実両眼のworld座標（代表値`z=-0.35m`）を記録し、裏・縁を見ます。追加薄膜は閉36indexとrayを保ち、通常描画は可視30index/1group/各眼1回だけであることをactual rendererのcallbackと照合します。後方席で白・部分白をHigh/Light・短い横移動で比べ、同じmain frameのscene/camera/atlasを保った薄膜on/off/restoreが正面のpixelを変えないことも確かめます。これは性能計測と分けた私用観測条件です。

床の帯を調べるときは、High/Light切替でrasterまで変える前に、同じcamera・照明・色map/UV・roughnessを保ってbumpだけを外し復帰します。shaderの再準備は必要でも、world時刻とsource frameを進めず同じnative描画で比べ、復帰像の一致を残します。色柄と法線の寄与を分けた後、近・遠・斜めと短い正規移動で材を評価します。静止した数値だけでHMDの時間品質を合格にしません。

`/tools/xr-color-probe.html` は材質・照明・テクスチャ・シェーダー・トーンマッピングを使わず、既知のRGB符号値を描画してアプリのGLバッファから読み戻す独立ページです。[HTML](../tools/xr-color-probe.html)と[TypeScript](../src/tools/XRColorProbe.ts)を[Viteの独立entry](../vite.config.mjs)としてビルドします。通常ゲームの読み込み・描画品質・設定には接続しません。画像・音声・外部通信・追加ライブラリはありません。

### 実行と結果の保存

1. `npm run dev` が表示するURLの `/tools/xr-color-probe.html` を開きます。配布ビルドは `npm run build` 後、`npm exec -- vite preview` の同じパスを使います。WebXRは信頼済みHTTPSまたはlocalhostで利用し、機器へ接続する手順は[別端末とVR](#別端末とvr)に従います。
2. 「通常画面を測定」で通常canvasの13パッチを取得します。ページを開いた直後にも1回取得します。11段階の灰色（0、4、8、12、17、24、32、48、64、128、255）と暗色17/23/27、32/16/8を、各viewportの左上から4列で並べます。未使用部分は96/96/96です。
3. VR利用時は「VR対応を再確認」を選び、表示時間5・10・15秒を指定して「VRの色見本を表示」を押します。この操作から直接セッションを要求し、各眼へ同じ配列を表示します。床や境界、手、カメラ、マイクは要求せず、`viewer` reference spaceだけを使います。
4. コントローラーの選択操作、ページの終了ボタン、Escape、本体の終了操作で終了できます。設定した時間にはタイマーとXR frame内の期限から終了を要求します。初期化のPromise待機中もタイマーは動きます。開始要求の取消または20秒の応答期限後に許可されたセッションも終了を要求します。終了拒否や3秒以内に終了を確認できない場合は、完了扱いにせず再試行と本体の操作を案内します。ページはブラウザー・OSの停止を強制解除できません。
5. 終了後の表と詳細JSONを確認し、「結果をJSON保存」を押します。通常とVRを別レポートで最新10回までページ内メモリーに保持します。再読込みや閉じる前に保存してください。

### 入力・参照値・実測値の区別

RGB8は光量ではなくバッファへ入れる符号値です。17/23/27なら `clearColor(17/255, 23/255, 27/255, 1)` とscissor付きclearを使います。8bit正規化RGB/RGBA格納を仮定したRGBA/UNSIGNED_BYTEの参照値は17/23/27/255ですが、実測結果とは別欄に置きます。追加の線形→sRGB変換は行いません。格納精度や丸めによる差を保存し、最大差1コード以内かを参考比較します。物理輝度や知覚品質の合否へ換算しません。

各パッチ中央3×3画素の全36byte、入力RGB8、clearの値、8bit参照RGBA、最大絶対差、patch/sample矩形、viewportと左下原点をJSONに保存します。ディザー・ブレンド・depthを無効にし、alphaは1で描き、AAは要求しません。通常画面はdefault framebuffer、VRは専用WebGL1 contextの従来型 `XRWebGLLayer` です。XR layerはalpha=false、倍率0.35を要求しますが、実装のclamp・丸めを含む実寸を記録し、要求倍率から推定しません。各フレームで見本を再描画し、readPixelsは最初の有効な姿勢で一度だけ行います。

XR互換化の `makeXRCompatible()` は正常なGPU移行としてcontext lossと復元を伴う場合があります。互換化中だけはそのPromiseの完了を待ち、復元後に色空間・ディザー・ブレンド・depth・書込みmaskを再設定します。未復元・拒否・取消・期限切れは測定を開始せず、表示開始後の予期しないcontext lossはレポートを未取得として終了要求します。

opaque XR framebufferへのbind・clear・readはXR animation callback内に限定し、attachmentの検査・変更は行いません。framebufferの完全性、channel bit数、layer種別・実寸、context属性を記録します。対応するcontextには `drawingBufferColorSpace='srgb'` を指定し報告値も保存しますが、これはXR attachmentやcompositor出力を実測した値ではありません。attachmentのcolor encodingは取得不可の理由を残します。projection layerの検証には一般化しません。

GL error、context loss、無効なframebuffer、pose/view/viewportの欠落、領域不足、例外、書き換わらない読取り先は、理由と未取得・`null` を保持します。白の確認用パッチを含む全ゼロ読取りは値を保存しても判定不能とし、参照比較を実施しません。上位レポートも未取得を引き継ぎ、空配列・0初期値・未実施を一致扱いにしません。「取得済み」はGL読取りの成立を示し、表示品質の合格ではありません。

## 実機での確認

この節と次節は所有者が運用中に使う手順です。[開発受け入れとの分離](agent-harness.md#実機確認と開発受け入れの分離)に従い、実機を使う時期や結果報告をIssue・PRの完了条件にしません。対象版、機器・接続・設定、手順、実施状況、結果と限界を開発の受け入れ欄とは別に記録します。未実施の実機結果を合格へ置き換えず、機器で観測した不具合は再現条件とともに修正対象として評価します。

ゲームパッドの両スティックと上下・モード切替を試します。ヘッドホンでは滝との距離や視点を変え、定位と音割れ・途切れの有無を確認します。

Windowsでリポジトリを開き、初回は `npm ci` を実行します。`npm run pcvr` は毎回ビルドし、同じPCから接続できる `127.0.0.1:4173` で起動して、既定のブラウザーへPCVR用URLを開きます。既定のブラウザーが別の場合は、WindowsのChromeで [http://127.0.0.1:4173/?vr=pc](http://127.0.0.1:4173/?vr=pc) を開きます。ループバックのHTTPはChromeで安全なコンテキストとして扱われます。ChromiumのWindows OpenXR VRは既定で有効ですが、ランタイムが `XR_EXT_win32_appcontainer_compatible` に対応する必要があります。この手順にADBやChromeの試験用フラグは不要です。 [Secure Contextsのループバック規定](https://www.w3.org/TR/secure-contexts/#is-origin-trustworthy) · [ChromiumのOpenXR対応](https://chromium.googlesource.com/chromium/src/+/HEAD/device/vr/README.md)

```sh
VIRTUAL_MONITOR_TLS_KEY=/path/to/lumen.key VIRTUAL_MONITOR_TLS_CERT=/path/to/lumen.crt npm exec -- vite preview --host 192.168.1.20
```

`192.168.1.20` をサーバーのLANアドレスに置き換え、表示されたポートを使って接続します。開発サーバーなら同じ環境変数で `npm run dev -- --host 192.168.1.20` を使えます。シグナリングにはこのViteサーバーが必要です。 `dist/` の静的配布では景観探索を起動できます。別端末同士の通信には、LANで相互に到達できることも必要です。[Viteのプレビュー設定](https://vite.dev/config/preview-options)

Quest 3 では純正のブラウザーで動作を確認します。LAN上のHTTPSを用意できない開発時は、開発者モードでUSB接続し、Android Platform Toolsの `adb devices` に機器が `device` と表示された状態で、`npm run dev -- --host 127.0.0.1 --port 5173 --strictPort` と `adb reverse tcp:5173 tcp:5173` を実行します。ヘッドセットで `http://localhost:5173/` を開きます。USB転送はヘッドセット内の閲覧確認用です。別端末からの共有も試す場合は、両端末が同じHTTPS URLを開けるLAN手順を使います。 [MetaのUSB転送手順](https://developers.meta.com/vr/documentation/web/browser-remote-debugging/) · [Metaのlocalhost対応](https://developers.meta.com/vr/documentation/web/port-vr-xr/)

1. 共有未接続で「VRを開始」を押し、左右の映像と頭の追跡を確認します。頭を横へ向け、左スティックで見ている方向へ進みます。右スティックを倒したままにして、30°の旋回が1回で止まることを確認します。
2. Xでファストトラベルを開き、丘陵展望台の2階、住戸の主寝室、映画館の座席へ移動します。各着地点、昼夜、座席の視点高を確認します。住戸のバルコニー引戸を右トリガーで操作します。映画館で試映し、頭の向きに応じた音の定位を確認します。
3. 「設定」でワールド照明を点灯・消灯し、既定に戻します。終了して通常画面の描画とマウス操作に戻ることを確認します。
4. 共有映像を接続して開始・移動・終了を試します。VR内の「仮想モニター」で音声をオフ・オンにし、動画と音声が同じ接続で続くことを確認します。グリップ、手のピンチ、両手での拡縮を試し、手を離すとモニターが固定されることを確認します。

住戸の向きによる描画は、ページを開き直し、`?world=residence&place=living-window&time=day` と `?world=residence&place=living-window&time=night` の両方で確認します。「VRを開始」が使えるようになったら入り、南窓から始めてテレビ側へ向きます。描画準備に失敗した場合は「描画準備をやり直す」で準備だけを再試行し、完了後に改めて「VRを開始」を押します。初めてテレビ側を向いたときと、元の向きに戻してからもう一度テレビ側を向いたときの追従を確認します。窓が片目の視野端に入るときも街が途切れず、キッチンを向いても映像が欠けたり追従が遅れたりしないことを確認します。主寝室から引戸を開けてバルコニーへ出入りし、昼にも窓とバルコニーの遠景を確認します。

展望台は `?world=overlook&place=main-deck&time=night` の中央デッキから街を向き、斜面や背後も見回します。上階でも左右に視線を動かし、建物の面と地形の境目で表示が飛ばず、視線に追従することを昼夜で確認します。

ブラウザー試験は模擬セッションです。Quest 3の機器上での接続と権限、フレームレート、レンズを通した表示、音声、物理コントローラーと手の追跡は実機で確認します。

### Windowsを配信元にする

LAN上の配信ページをWindowsのChromeで開き、同じコードで視聴先に接続します。Windowsでテスト用ウィンドウと画面全体をそれぞれ選び、入力した映像と音声が届くかを確認します。音声の有無は共有ダイアログと返されたトラックに従います。Windows機での取得・音声・PCVRは未検証です。
