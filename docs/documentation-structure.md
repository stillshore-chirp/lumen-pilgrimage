# 文書の責務と更新基準

この文書は、Lumen Pilgrimage の現行文書の正本、更新条件、内容の受け入れ基準を定めます。文書を追加するときは、対象読者と正本の責務を決め、README からたどれる入口を用意します。

| [docs/agent-harness.md](agent-harness.md) | エージェント向けの Issue・PR 記載、文書更新の入口、ハーネス検査の案内をまとめます。 | GitHub での作業記録、静的検査の対象や手順が変わるとき。 |
| [Codex ワークツリーの環境設定](../.codex/environments/environment.toml) | Codex が作成するワークツリー向けの依存セットアップを定めます。 | Codex ワークツリーの依存セットアップが変わるとき。 |

## 内容の受け入れ基準

文書の変更は、対象となる実際の利用、設計、資産、開発作業に結び付けて確認します。

- 変更された契約や事実を特定し、この表の正本を更新します。影響を受けない文書を形式的に変更しません。
- 手順には、必要な前提、実行する操作やコマンド、期待する結果を記します。ツールの操作条件や制限が結果に影響する場合はそれも記します。
- 設計や再現手順には、根拠となる資料または実装の場所、必要な寸法・座標系・視点・時刻・設定、確認する結果を、該当する範囲で記します。
- 出典、ライセンス、再配布条件は該当するクレジットファイルを確認し、採用・加工・生成の記録から分かるようにします。権利や利用条件を確認できない素材は確定事項として記載しません。
- 直接確認した事実、資料からの推論、未確認事項を区別します。未確認の挙動や不明な前提を、動作確認済みとして扱いません。
- 素材の追加・差し替えでは、編集可能な原本または取得元、ライセンスと出典、使用ツール・版・設定・コマンド、生成物と実行時の制約、検証方法と結果、証拠として残せなかった点を記録します。値が入手できない項目は未確認として明示します。
- 次の担当者が会話履歴なしで作業を再開できるよう、関連するコード・資料・検証入口を示します。作業中の進捗や判断の履歴は Issue または作業計画へ記録し、安定した仕様文書へ時系列の状態を混ぜません。
- 同じ事実が複数のページに必要な場合は、正本に詳細を書き、他のページには短い案内とリンクを置きます。

## 素材の受け入れ記録

素材を追加・差し替え・再現するときは、利用条件と実行可能性を次の項目で記録します。取得できなかった値や残った不確実性は、未確認として明示します。

| 項目 | 記録内容 |
| --- | --- |
| 原本・取得元 | 編集可能な原本の場所、または配布元・取得先と識別情報。 |
| 出典・利用条件 | 権利者、ライセンス、必要な表示、改変・再配布条件。該当する `ATTRIBUTION.md` を更新します。 |
| 作成・加工 | 使用ツールと版、設定値、実行コマンド、入力素材から出力までの手順。 |
| 出力・実行条件 | 生成物の形式・配置、実行時の依存や制約、対象ブラウザー・品質設定などの条件。 |
| 検証・証拠 | 代表的な手順、期待結果と実結果、確認用画像・音声・ログの参照先、未確認の範囲。 |

## 更新と受け入れ

1. 変更対象の動作、設計、素材、開発手順、運用手順を特定し、対応する正本と未解決の前提を確認します。
2. 正本を更新し、入口や関連資料から新しい情報をたどれるようリンクを整えます。新しい現行ページは README から到達できる状態にします。
3. 文書変更では `npm run validate:harness` を実行します。機能・描画・音響・移動などを変えた場合は [検証と配布ビルド](verification.md) の該当ゲートを実行し、未実施の確認と理由を記録します。
4. 受け入れ時に、変更した事実と正本、未解決事項、実際に行った検証と結果が追えることを確認します。静的検査はリンクや配置の確認であり、記述内容や実機動作の証明には使いません。
5. 新規または手順を実質変更した引き継ぎ・再現手順は、代表的な環境で少なくとも1回実行し、条件、期待結果、実結果、確認できなかった範囲を記録します。実機や外部環境を使えない場合は、代替確認とその限界を明記します。

PR には「変更した契約・事実 → 更新または確認した正本 → 実施した検証または文書影響がない理由」を記録します。文書差分の有無だけでソース変更を機械的に判定しません。
