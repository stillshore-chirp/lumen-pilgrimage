# 仮想モニターの技術仕様

このページは、仮想モニターの統合状態、シグナリング、メディア配信、配置、対応環境の契約をまとめます。利用者の操作は[探索ガイド](exploration.md#仮想モニター)、設計の概要は[アーキテクチャ](architecture.md#仮想モニターの設計)、試験手順は[検証と配布ビルド](verification.md#仮想モニターの実機確認)を参照してください。

## 起動と構成

- 通常の景観ページは受信側パネルを表示します。`?monitor=sender` を付けると、`src/main.ts` が配信ページを起動します。配信ページはブラウザーの画面選択ダイアログから取得した映像・音声を送ります。
- シグナリング API は `/api/virtual-monitor/{action}` です。`vite.config.mjs` のプラグインが Vite の開発サーバーとプレビューサーバーにだけミドルウェアを登録します。`dist/` を静的配信するだけでは API がなく、ペアリングできません。
- 画面・音声はシグナリングサーバーを通らず WebRTC で端末間に送ります。サーバーは一時的なペアリング状態と SDP をプロセス内メモリーに持ちます。録画・永続保存はしません。
- 画面取得と WebRTC に安全なコンテキストが必要です。localhost の HTTP はブラウザーの安全なコンテキスト例外として利用できます。別端末から使うときは、両端末が同じ信頼済み HTTPS URL を開き、互いに直接到達できるネットワークに置きます。

LAN 用 TLS の起動例と証明書の置き場所は[検証手順](verification.md#別端末とvr)を参照してください。秘密鍵と証明書はリポジトリ外に置きます。

## シグナリング契約

各 POST は `application/json` を使います。`create` と `join` 以外は、ペアリング時に割り当てられた役割別トークンを `Authorization: Bearer …` で送ります。リビジョンが変わるたびに snapshot を更新し、待機中の poll を起こします。

通常の要求と成功応答の形は次のとおりです。コードとトークンは形式を示すプレースホルダーです。

```text
POST /api/virtual-monitor/create
{}
→ {
  "sessionId": "<session-id>",
  "token": "<sender-token>",
  "code": "XXXX-XXXX-XXXX",
  "snapshot": {
    "revision": 0,
    "phase": "waiting",
    "audio": { "available": false, "output": "both" }
  }
}

POST /api/virtual-monitor/join
{ "code": "XXXX-XXXX-XXXX" }
→ {
  "sessionId": "<session-id>",
  "token": "<viewer-token>",
  "snapshot": {
    "revision": 1,
    "phase": "pending",
    "verification": "<six-digit-number>",
    "audio": { "available": false, "output": "both" }
  }
}
```

それ以降の要求は共通の `sessionId` と役割トークンを使います。`poll` は `{ "sessionId": "<session-id>", "revision": 1 }`、`approve` は `{ "sessionId": "<session-id>", "accept": true }`、`offer` と `answer` は `{ "sessionId": "<session-id>", "description": { "type": "offer", "sdp": "<complete-sdp>" } }` の形です。`answer` では `type` を `answer` にします。`audio` は `{ "sessionId": "<session-id>", "audioSequence": 1, "audio": { "available": true, "output": "both" } }`、`close` は `{ "sessionId": "<session-id>" }` です。

`create` は `sessionId`、`token`、`code`、`snapshot` を返し、`join` は `sessionId`、`token`、`snapshot` を返します。それ以外の成功応答は `{ "snapshot": { … } }` です。snapshot には常に `revision`、`phase`、`audio` があり、`verification`、`offer`、`answer` はその状態で値がある場合にだけ含まれます。音声情報の `pcPlaybackSuppressed` も必要な状態でだけ含まれます。承認済みの応答には `authorization` が加わり、応答生成時点から承認上限までの `approvalRemainingMs` と、両端末のうち先に通信が途絶えた側の失効までの `activityRemainingMs` をミリ秒で返します。既存クライアントはこの追加項目を無視できます。更新後のクライアントは期限を返す同梱のシグナリングサーバーを使います。すでに開いている共有へ端末側の期限を適用するには、配信・視聴の両方のページを更新し、新しいコードで接続します。

| action | 実行できる側 | 契約 |
| --- | --- | --- |
| `create` | 認証前 | 配信側セッションと 12 桁の大文字コードを作成します。コードは表示上 `XXXX-XXXX-XXXX` に区切られます。 |
| `join` | 認証前 | コードから空白・ハイフンを除き、大文字小文字をそろえて照合します。成功すると視聴側を 1 件だけ予約し、6 桁の確認番号を発行します。 |
| `poll` | 配信側または視聴側 | 役割のトークンと安全な整数の `revision` が必要です。同じ役割から同時に複数の poll はできません。 |
| `approve` | 配信側 | `pending` の間だけ `accept: true/false` を受け付けます。拒否はセッションを閉じます。承認は確認番号を破棄して `approved` に進めます。 |
| `offer` | 配信側 | 承認後に一度だけ送れます。description の type は `offer`、SDP は空でない文字列である必要があります。 |
| `answer` | 視聴側 | 承認後に offer が届いた場合だけ一度送れます。description の type は `answer`、SDP は空でない文字列である必要があります。 |
| `audio` | 配信側 | `available` は boolean、`output` は `pc`・`viewer`・`both` のいずれかです。PC 側の再生抑止情報を付ける場合は、音声あり・`pc` 出力の組み合わせだけを受け付けます。設定を変更するたびに正の整数 `audioSequence` を増やします。古い番号や重複は設定と生存確認の時刻を更新しません。従来の番号なし要求は、その共有で番号付きの最初の更新が受理されるまで使えます。 |
| `close` | どちらの役割も | セッションを閉じ、コード、確認番号、SDP、役割トークンを破棄します。 |

配信側のコードは発行から 120 秒で失効し、1 件の視聴先が join すると再利用できません。承認後は 8 時間で失効します。承認後、配信側または視聴側のどちらかから 90 秒間、認証済みリクエストが届かない場合も閉じます。通常は poll がこの生存確認を担います。poll は最大 10 秒待ちます。サーバーの終了時には全セッションを閉じます。

リクエスト本文は 64 KiB、SDP は UTF-8 で 32 KiB が上限です。API は同一オリジンの POST のみを受け付けます。送信元の役割と現在の phase に合わない操作、同じ方向への二度目の SDP は拒否されます。これらは正常なペアリング・交換の前提であり、別オリジン配信や多人数ルームは提供していません。

実装は[シグナリングサーバー](../server/virtual-monitor-signaling.mjs)と[クライアントセッション](../src/monitor/monitorSession.ts)にあります。

シグナリングエラーの HTTP 応答は `{ "error": "<code>" }` です。

| HTTP | 正常な統合での意味 |
| --- | --- |
| `400` | JSON 本文、revision、承認、音声設定、description の形式が不正です。 |
| `401` | ペアリング後の要求に有効な Bearer トークンがありません。 |
| `403` | オリジンが一致しないか、その役割では実行できない操作です。 |
| `404` | 操作名、コード、セッションが存在しないか、期限切れです。 |
| `409` | 現在の phase では実行できない操作、重複した SDP、または同じ役割の poll が進行中です。 |
| `413` | JSON 本文または SDP がサイズ上限を超えています。 |
| `429` | リクエスト予算、同時処理数、セッション数の上限に達しています。 |
| `503` | シグナリングサーバーが終了処理中です。 |

## 接続、切断、失敗時の状態

サーバー phase は `waiting → pending → approved → closed` です。画面に出すクライアント状態は `idle`、`waiting`、`approval`、`connecting`、`connected`、`ended`、`failed` で、phase と通信状態をまとめています。

1. 配信側はユーザー操作中に画面選択ダイアログを開きます。映像トラックが必要で、音声トラックは任意です。取得後に `create` し、コードを表示して視聴先を待ちます。
2. 視聴側がコードを送ると、両画面に同じ確認番号が表示されます。利用者が番号を照合して配信側で許可するまでは、WebRTC peer を作らず、画面トラックも送信しません。
3. 承認後、配信側が offer を作り、視聴側が answer を返します。両側は ICE 候補の収集完了を待ってから SDP 全体を交換します。トリクル ICE は使いません。
4. クライアントは `RTCPeerConnection({ iceServers: [] })` を使います。シグナリング API が交換するのは offer・answer・音声状態で、映像・音声の経路は WebRTC です。外部 STUN/TURN サーバーは設定されていません。別端末間では直接接続できるネットワークが必要です。
5. 接続中も両端末が poll して生存を知らせます。配信側の共有停止、視聴側の切断、映像トラックの終了、接続障害の確定、セッションの終了・失効時にメディアを解放します。音声トラックだけが終わった場合は映像を続け、音声を利用不可として通知します。

クライアントのシグナリング要求は 15 秒、ICE 候補収集は 8 秒、接続確立は 30 秒、WebRTC の `disconnected` 状態からの猶予は 5 秒です。接続確立に失敗したときや接続が終了したときは、配信側で共有を開始し、新しいコードで接続します。

確立済みの接続で映像トラックが `live` の間は、通信エラー、要求のタイムアウト、前の poll の処理中（`409`）、要求制限（`429`）、一時的なサーバーエラーが起きた poll を、同じセッションと最後に受け取った revision で再試行します。待機間隔は 1 秒から最大 8 秒まで段階的に延ばします。その間も同じ接続とトラックを使います。サーバーからセッション終了や期限切れの通知、認証・権限エラーを受け取った場合は終了します。応答が途絶えても、端末は確認できた承認と生存確認の期限の早い方で接続とメディアを解放します。有効な応答を受け取った場合に限り生存確認の期限を更新します。承認の上限は延長しません。WebRTC 自体の切断猶予も適用します。

メニューの開閉、映像面の表示・非表示と表示先、住戸の照明、時間帯や描画品質の変更中も共有を維持します。視聴ページの `pagehide` でブラウザーが履歴キャッシュへの保持を通知した場合は、既存の接続とメディアをページに残します。視聴ページの通常終了と配信ページからの離脱では接続とメディアを解放します。

同じワールド内のファストトラベルでは、受信接続とワールド座標上の映像面の配置を維持します。WebXR 中は視聴者の XR rig を移動後の視点へ合わせ直します。

接続中または配信元の承認待ちに別ワールドへ移動すると、移動先を読み込んでからシーンと操作パネルを交換します。同じビデオ要素、WebRTC 接続、受信メディア、音声コンテキストを使い、同じ文書内の履歴を戻る・進むときも引き継ぎます。シーンの切り替え時は、元のテレビや映画館スクリーンから映像を外し、到着先で浮遊表示に切り替えます。音量、モニター音声のオン・オフ、ヘッドホンのステレオまたは浮遊モニター左右からの再生の選択を保持し、設備専用の音響からは浮遊モニター左右からの再生へ切り替えます。移動先の読み込みに失敗したときは元のワールドで視聴を続けられます。[移動処理](../src/coast/CoastApp.ts) · [パネルと映像面の引き継ぎ](../src/monitor/monitorView.ts)

## 同じ端末からの接続

視聴パネルの「この端末から共有」は、同じオリジンの配信ページを利用者のクリックで開きます。配信側の画面選択後、発行された一回コードを元の視聴ページへ渡し、手入力を省きます。確認番号を照合して配信側で許可するまでは、従来どおり peer を作らず、メディアも送りません。別端末やポップアップ制限時は既存の手動コードを使えます。

コードの受け渡しは、開いたウィンドウとの `origin`・`source`・メッセージ形式の照合後に転送した `MessagePort` を使います。配信ページは初期化時に `window.opener` を解除します。コードと役割トークンを URL、履歴、referrer、永続ストレージ、共有 broadcast channel へ保存しません。役割トークンは渡さず、シグナリング API が役割ごとに発行します。受け渡しは一回だけで、起動から2分、再試行、停止、ページ離脱、破棄時に終了します。配信ページの選択に2分以上かかった場合も、画面に表示された有効なコードを手入力できます。サーバー側のコード期限・一回利用・配信側承認・失効条件は変更しません。

根拠は [HTML Standard 9.3.2–9.3.3 と 9.4](https://html.spec.whatwg.org/multipage/web-messaging.html#security-postmsg) の送信先オリジン、受信元・形式確認と channel messaging です。実装は[ローカル接続](../src/monitor/monitorPairing.ts)と両パネルにあります。

## 映像の滑らかさと計測

画面取得は `frameRate: { ideal: 60, max: 60 }` を要求し、映像トラックの `contentHint` を対応時に `motion`、送信用 encoding の `maxFramerate` を60にします。動きを優先するため、帯域や処理負荷が不足する場合はブラウザーが解像度・画質を下げることがあります。送信用の `maxBitrate` は開始時の入力画素数×入力fps（最大60）×0.1bit/pixel/frameを2〜12Mbpsに収めた工学的な上限とします（720p60で約5.53Mbps）。最低送信量を強制せず、ネットワーク・CPUに応じた適応を維持します。この予算は画質や到達fpsの保証値ではありません。固定ビットレート、フレーム補間、SDPの書き換えは行いません。

60fpsは目標であり、取得元が15/30fps、OS・ブラウザー・encoder・通信・描画に制約がある場合に60fpsへ変換するものではありません。[Screen Capture 5.4・5.4.1](https://www.w3.org/TR/screen-capture/#constrainable-properties) は取得元と制約による間引きを定義し、追加フレームの生成を認めていません。[Content Hints 3.2・4.3](https://www.w3.org/TR/mst-content-hint/#video-content-hints) の `motion` はフレームレート保持を優先する助言です。[WebRTCのencoding設定](https://www.w3.org/TR/webrtc/#dom-rtcrtpencodingparameters-maxframerate) の値も上限であり、到達保証ではありません。

接続中の「映像の滑らかさを計測」は、前面のページで3秒間、`getStats()` の累積カウンター差と各統計の時刻差から fps を求めます。配信側は取得元 `media-source.frames`・encoder `framesEncoded`・送信 `framesSent`、視聴側は受信 `framesReceived`・デコード `framesDecoded` を分けます。視聴側の「映像フレーム更新」は `requestVideoFrameCallback` の `presentedFrames` の差（先頭観測の1枚を含む）を、更新が止まった時間も含む全観測区間の単調時計の経過時間で割ります。観測窓の終了時にcallbackを取り消して分子を固定し、その後の最終統計取得の待機中は加算しません。表示面の開始・終了カウンターも取得時の値で固定します。RTC統計は各timestampの差、映像更新は `presentationDurationMs`、表示面は `surfaceDurationMs` を使うため、各層の期間を区別します。初回callbackまでの待ちや主スレッドの処理遅延により、実際のcompositor更新より少なく観測される場合があります。これは video の compositor 提出であり、Three.js の描画回数、HMDの走査や実画面のフレームレートではありません。「景観描画」は浮遊面・テレビ面を主カメラ（XRでは左右の目）で実際にdrawした回数、「景観への映像供給」はrVFC対応時に限り、`Texture.onUpdate` でupload APIへの提出を確認した新しいVideoTextureのversionを、そのdrawに使った回数として測ります。主表示先と異なるrender target、反射・影・副カメラを除き、同じ描画tickの複数passと左右の目は重複計上しません。映画館の専用投影shaderや非表示中はこの面の計測対象外として「未取得」にします。rVFC非対応ではThreeのfallbackが同じ映像を描画毎に再提出できるため、描画・uploadのfpsは保持し、新映像の供給fpsだけを「未取得」にします。未対応を0fpsや再提出のfpsへ置き換えません。version更新、upload API提出、main draw提出、compositor更新を分けます。raw診断の `uploadFps` は共有texture全体へのAPI提出であり、反射などを除いたmain描画のfpsとは別です。`onUpdate` もGPUでの転送完了や実画面の走査完了を保証しません。景観側は同じVideoTextureを更新し、別の30fps制限を加えていません。hiddenのvideoに対する `VideoPlaybackQuality` のDOM表示/dropカウンターは、3D映像面の表示数を表さないため補完には使いません。診断でもこの組み合わせは未対応として扱います。観測方法はThree.js 0.184.0の `VideoTexture`・`WebGLTextures`・`WebGLRenderer` 実装と、[onAfterRender](https://threejs.org/docs/pages/Object3D.html#onAfterRender)・[Texture.version](https://threejs.org/docs/pages/Texture.html#version) の契約を照合しています。

カウンター欠測、統計IDの変更、リセットは0fpsへ置き換えず「未取得」とします。背景化した区間は結果を採用せず再計測を案内します。診断は利用者の操作時だけ行い、SDP、ICEアドレス、トラック名を診断結果へ出しません。原典は [WebRTC Statistics 8.5・8.8・8.13](https://www.w3.org/TR/webrtc-stats/) と [Video Frame Callback 2.2](https://wicg.github.io/video-rvfc/#video-frame-callback-metadata) です。[計測実装](../src/monitor/monitorVideoMetrics.ts)・[表示面のdraw観測](../src/monitor/monitorObject.ts)・[検証手順](verification.md#仮想モニターの実機確認)を参照してください。

## 画面と音声

配信側は `getDisplayMedia()` に映像と音声を要求します。共有ダイアログが音声トラックを返さないときは映像のみで動作します。音声の出力先は次のとおりです。

| 選択 | 動作と条件 |
| --- | --- |
| PC側のみ | 音声トラックの送信を止め、視聴側を無音にします。ブラウザーが共有タブの PC 側再生を抑止中の場合、PC 側で音を戻すには共有対象を選び直します。 |
| VR側のみ | 共有中のブラウザータブについて、ブラウザーが PC 側のローカル再生抑止を報告した場合に使えます。条件を満たさない場合は「両方」に戻るか、タブを選び直すよう案内します。 |
| 両方 | 共有対象から音声トラックが得られた場合に、PC 側と視聴側へ送ります。 |

出力先の変更は配信側の音声トラックに先に適用します。確立済みの映像が続いている間に視聴先への設定通知が一時的な通信障害で失敗した場合は、同じ接続で間隔を延ばして再送します。「音声の設定を視聴先に反映中です。」と表示されている間も、出力先を変更したり共有を停止したりできます。通知は一件ずつ処理し、再送には最新の出力先と音声トラックの状態を使います。

画面全体の音声を同じ PC で共有すると、視聴側の音が配信側へ戻ることがあります。視聴側で「モニター音声」をオフにする、配信側で「PC側のみ」を選ぶ、音声を出すタブだけを共有する、のいずれかで回り込みを防げます。OS の選択ダイアログ、権限、共有対象が返すトラックによって音声の有無が決まります。[キャプチャの判定](../src/monitor/monitorCapture.ts) · [配信ページ](../src/monitor/monitorSender.ts)

受信側の video 要素はミュートして映像を表示し、音声は受信トラックを専用 Web Audio グラフで再生します。ブラウザーが映像再生を止めた場合はパネルの「映像を再生」を押します。共有音声は接続ごとにオフから始まります。「モニター音声」を押すとブラウザーの音声再生を開始し、同じボタンで開始の取り消し、オフ、再試行ができます。音声なし、または「PC側のみ」のときはボタンが「停止中」になります。同じ接続で配信元が出力先を戻すと、視聴側で選んでいたオン・オフが適用されます。モニター音量とオン・オフは環境音から独立し、ステレオまたはモニター位置に応じた空間音響を選べます。[受信パネル](../src/monitor/monitorView.ts) · [音声グラフ](../src/monitor/monitorAudio.ts)

浮遊表示の既定は「モニター左右から」です。実際に映像を収めた面の左右縁に、描画しないL/R音源を置きます。標準のステレオ変換後に左右を離散分離するため、モノラルは両側へ入り、反相ステレオは中央でモノラル化されません。映像の縦横比、拡大、回転、移動に音源が追従します。「ヘッドホンのステレオ」では空間配置を外した左右再生を選べます。 [チャンネル処理と空間化の原典](https://www.w3.org/TR/2026/WD-webaudio-1.1-20260922/#ChannelSplitterNode) · [表示面の音源](../src/monitor/monitorObject.ts)

ワールドは、浮遊表示の2音源、テレビの単点音源と6チャンネルのスピーカーを、そのワールドの音場へ接続する同期factoryを任意で供給できます。テレビの単点入力は明示的にモノラルへ変換し、6チャンネルは L・R・C・LFE・SL・SR の順を維持します。モノラル音源はC、ステレオ音源はL/Rへ入り、LFEの120Hzローパスは共有側で一度だけ適用します。音場側が距離・壁や扉・到来方向・HRTFを処理する場合、従来のPannerを直列には接続しません。factoryを供給しないワールドは左右別の空間Pannerを使い、ヘッドホンのステレオと映画館の経路はそれぞれ独立しています。

商業アトリウムでは「館内スピーカー」と「カフェのスピーカー」を追加で選べます。館内18台は3層の側壁、カフェ6台は[カフェ共通平面](../src/coast/world/atrium/atriumCafePlan.ts)の客席側に置き、描画と音響が同じ位置・向きを使います。ステレオの基準は館内が−Z方向、カフェが入口から奥の＋X方向です。カフェでは入口から見た左壁（local uの高い側）へLを送り、機器IDの末尾をチャンネル順の代用にしません。台別の左右重み、短い遅延と位相応答を変え、距離・向き・遮蔽による利得と帯域を更新します。近接時の同相信号の合計を抑え、音量は受信側の選択音量へ戻します。カフェの外で聞くカフェ音声と、店内で聞く館内音声は入口経由へ切り替えます。店舗の閉じた壁を直通する定位にはしません。

カフェ内の反射は床・天井の一次鏡像2本、後期成分は既存の屋根下用応答を使う近似です。カフェ全体の幾何学的室内応答の解や実測IRとは扱いません。備品室の共通隔壁を横切る経路では利得と高域を下げ、床・天井反射を除きます。館内は既存の `atriumSoundPath` と吹抜／屋根下の応答を使います。左右入力は別の残響応答を持ちます。出力先選択は視聴側だけの再生経路を変え、映像面・共有トラック・WebRTC接続を保持します。 [館内の配線と伝搬](../src/coast/world/atrium/atriumMonitorAudio.ts) · [映画館の57出力](cinema/cinema-sound-design.md#画面共有と試映)

音場側は渡されたAudioContext内に自分のノードを作り、すべての直接音・残響を共有側のモード音量へ返します。モード切替と最終音量・消音はその後に適用します。共有側は受信トラック・音源ノード・AudioContextとlistenerを所有し、音場側へは初期化済みの音源・聴取姿勢と品質設定を渡します。映画館と選択式の館内出力には、共有側が所有する入力分岐とモード出力を置きます。音場の解放が例外を返す場合も、この両端を切り離して残る枝の解放を続けます。ワールド移動では旧音場の入力と参照を解放してから旧ワールドを破棄し、受信メディアを保持します。音場の生成・更新に失敗したモードは利用不可とし、利用可能なステレオへ戻します。他の正常なモードは保持します。

ワールドの読み込みが成功し、再構築・廃止する音場が再生中の場合は、旧ワールドが生存している間に共有音声を24msで下げます。32msの待機後に表示先と音場を同期して切り替え、その後24msで現在の音量へ戻します。受信メディアと音源は停止せず、途中で変更した音量や消音状態も保持します。読み込みの取消・失敗・画面終了では音量遷移を解放します。同じステレオ・浮遊音源の経路が続く場合や音声オフ・音量0では適用せず、照明・パネル・描画品質などの操作にも適用しません。

## 表示面、配置、WebXR

視聴側はワールド座標に映像面を置きます。未接続時と既定配置の基準寸法は 16:9 です。映像を再生すると、表示面は共有メディア本来の縦横比に合わせて枠内に収まります。初回表示または「位置・サイズを戻す」では視線の前方、通常は約 3.25 m 先へ置きます。縦長画面では画面比率に合わせて距離を調整し、サイズは既定位置に対して 0.25〜5 倍に制限します。非表示にしている間も配置はそのページ内で保持され、再読み込み後には保持されません。[映像面](../src/monitor/monitorObject.ts)

デスクトップでは「配置を編集」を選び、移動・回転・拡大縮小を選択して映像面をドラッグします。画面の外をつかんだドラッグは始まりません。編集は `Esc` で終わります。モニターは浮遊表示のほか、対応するシーンのテレビや映画館スクリーンへ接続中の映像を表示できます。[デスクトップ配置](../src/monitor/monitorDesktop.ts) · [表示先](../src/monitor/monitorView.ts)

パネルを閉じた探索画面では、表示中の浮遊モニターを照準に入れ、`F` で掴めます。視点との相対位置と向きを保って移動させ、もう一度 `F` を押すとワールド座標に固定します。パネルを開く操作、表示先や表示状態の変更、XR開始時にも保持を解除します。 [掴みの実装](../src/coast/DesktopGrab.ts) · [表示と解除](../src/monitor/monitorView.ts)

探索画面とモニターパネルは同じ[没入型セッション](../src/xr/ImmersiveSession.ts)を開始します。WebXR は `local-floor` を必須、`hand-tracking` を任意に要求します。モーションコントローラーは映像面に照準を合わせ、squeeze/grip でつかみます。手の追跡があるときは親指と人差し指の pinch を使えます。片手で移動・回転し、左右の手を使って拡大縮小できます。追跡を失う、セッションを終了する、またはモニターを隠すと掴みを解除します。視聴の途中でVRを終了しても同じ接続で再生を続けます。 [モニターのXR入力](../src/monitor/monitorXR.ts) · [VR探索の操作](exploration.md#meta-quest-3-で探索する)

## 対応条件と確認済み範囲

| 環境・機能 | 実装条件 | リポジトリに記録された確認範囲 |
| --- | --- | --- |
| 画面共有 | 安全なコンテキスト、`getDisplayMedia()`、`RTCPeerConnection`、`MediaStream` が必要です。 | 操作ガイドは Mac の Chrome を案内します。自動テストではピッカー API だけを合成し、canvas と Web Audio のトラックを実際の WebRTC で二つのタブ間に送ります。OS の画面選択や許可ダイアログを検証したことにはなりません。 |
| macOS | 画面共有と音声のコード経路は共通です。Chrome の画面収録・システムオーディオ録音許可が結果に影響します。 | [手動手順](verification.md#macの画面と音声)はあります。自動テストは macOS の実画面選択と OS 音声経路を確認しません。現在の検証記録には実機手順の実施結果がありません。 |
| Windows | 同じ画面取得とトラック契約を使います。実際に返る音声トラックはブラウザーと選択対象に依存します。 | Windows 機での画面取得・音声・PCVR は未検証です。[配信元の手順](verification.md#windowsを配信元にする)を実機で確認してください。 |
| WebXR | `navigator.xr` が immersive VR をサポートし、必須 reference space を取得できる必要があります。 | 単体テストの入力はモックです。ヘッドセットと別端末を使う実接続、実機の controller/hand tracking は[実機手順](verification.md#別端末とvr)で別に確認します。 |

このページの API 条件はコード上のガード、確認範囲は現在の文書とテスト構成に基づきます。macOS、Windows、ヘッドセットで実際に使えることを自動テストから推定しません。Linux やブラウザーの版別サポートは、現行文書に確認記録がありません。

## トラブルシューティング

| 表示・症状 | 確認と対応 |
| --- | --- |
| HTTPS または localhost が必要 | 配信側・視聴側とも安全な URL を開きます。別端末では信頼された HTTPS URL を使います。 |
| ブラウザーが共有に対応していない | `getDisplayMedia()` と WebRTC が使えるブラウザーで開きます。権限がある URL から操作してください。 |
| 共有がキャンセルされた・許可されなかった | 配信ページの「画面共有を開始」を押して、ブラウザーの画面選択を完了します。 |
| 画面を取得できない | macOS ではシステム設定の「プライバシーとセキュリティ」から Chrome の「画面収録とシステムオーディオ録音」権限と再起動要求を確認します。他の OS でも画面共有権限と選択対象を確認します。 |
| コードを使えない | コードの発行から 2 分以内に接続し、配信側で現在表示中のコードを使います。コードは視聴先 1 件で消費されるため、配信を再開して新しいコードを発行します。 |
| 確認番号の後も接続できない | 両画面の 6 桁の番号を照合してから配信側で許可します。接続が 30 秒で失敗する場合は、両端末が同じ HTTPS サーバーを使い、ネットワークが WebRTC の直接接続を許可する環境か確認します。システムに STUN/TURN 中継はありません。 |
| 共有映像が表示されない | 接続状態を確認し、映像再生が求められたら「映像を再生」を押します。配信側で共有を停止した場合は新しいコードで接続します。 |
| 視聴側で音が出ない | 配信側で共有音声トラックが取れているか、出力先が「PC側のみ」になっていないか確認します。視聴側では「モニター音声」をオンにします。「VR側のみ」は音声付きタブを選び、PC 再生抑止が確認できる場合に限ります。 |
| 音が配信側へ回り込む | 同じ PC の画面全体を共有している場合は、視聴側で「モニター音声」をオフにするか、配信側で「PC側のみ」を選びます。 |
| 「VRで見る」が使えない | ブラウザーが immersive VR を提供するか、接続した機器が対応しているかを確認します。XR セッション開始が拒否された場合は、画面の状態表示を確認してユーザー操作から再試行します。 |
| ファストトラベル後に映像面を見つけにくい | 同じワールド内の移動では接続とワールド配置が続きます。視点の前へ置き直すには「位置・サイズを戻す」を押します。別ワールドへの到着時は視線の前へ再配置します。映像面を隠していた場合は「モニターを表示」を押します。 |

## 再現・検証の入口

- `npm run test:monitor` はシグナリング、接続、キャプチャ判定、映像面配置、WebXR モック、音声グラフの単体テストを実行します。
- ビルド後の `COAST_CHROME_CHANNEL=chrome npm run test:monitor:browser` は二つのタブを使い、合成キャプチャから実ブラウザーの WebRTC 映像・音声、配置、切断と解放を確認します。詳細な条件は[ブラウザー回帰テスト](verification.md#ブラウザでの回帰テスト)にあります。
- macOS の画面選択と OS 音声、Windows の画面・音声、別端末のネットワーク経路、実機 WebXR は自動テストから切り離し、[仮想モニターの実機確認](verification.md#仮想モニターの実機確認)に従って確認します。
