# 映画館再評価の検証範囲

これは有限の入力と出力を照合した記録です。全館の完成判定、所有者のWindows・物理HMDの運用結果や、特定設備の認証を示しません。仕様は[上映音響](cinema-sound-design.md)、[機器取付](cinema-speaker-mounts.md)、[還気口](cinema-ventilation.md)、実行手順は[検証ガイド](../verification.md#映画館の機器接続と接近)を参照します。

## スクリーン背面の是正候補

C13の静止模擬XRでは、body `z=0.65 m`を保ったまま実両眼が`z=−0.35 m`へ回り、客席方向を見ると正面用片面Planeが描かれず客席が透過して見える欠落を確認した。前側の実眼`z=0.25 m`からの客席方向像と区別して保存した。許可頭部包絡の既知不合格であり、通常飛行の正面停止を背面品質の証拠にしない。

C14では1.2mmの閉薄膜を追加したが、後方席の白投影に細かな黒斑が生じた。0.5mmの正面gapと描画順−1だけでは、異なる三角形・instance変換の深度誤差を排除できない。前側capの重複描画を除く候補は[幕の裏面と縁](cinema-sound-design.md#幕の裏面と縁)のとおり。実factoryの正面・背面・四辺ray、四周の体積接触、可視30/非表示6 indexのgroup、受光shader、専用geometry/非表示材/既存共有材の一度の解放をCPUで照合する。C15の同じ実眼からの裏面、前後・斜めの縁、後方の白/部分白・High/Light・微動、通常正面上映と状態復帰の直接像は候補段階では未実施。C13の成功した音声・移動などは入力閉包が同じ範囲だけ再利用する。

## 床の色柄と凹凸の切り分け

C14の元R01-standing-frontと同じcamera・service・High・1920×1080/DPR1で、床2材のbumpMapだけを同じrender task内で無効化・復帰した。colorMap・UV・roughness・bumpScaleは不変、復帰PNGは全pixel同一だった。可視段床ROIの501600pixelではon/off差が最大RGB1、RMS差0.002704で、幅広い帯は残った。bump無効を製品の解決とはせず、規則的な色柄を主因候補として分離した。

候補は[床の表面](cinema-sound-design.md#床の表面)の床専用grain。実factoryの他画像・形・支持・材参照・texture数、旧波の周波数成分と実byte範囲を比較する。C15同pose・近接・遠方・短い微動・High/Lightの直接像は候補段階では未実施。静止像からHMDの無ちらつきを保証しない。

## Native offlineと環境音の観測

C12固定版の標準音響targetでは、5代表席×2品質を含む21 response＋30 clarityの51 native OfflineAudioContextが全てclosedとなり、既存63 assert式とgesture・4mix・足音・preview切断・disposeの検査を保持して142.149秒で完了した。製品source333・dist103と元testの開始前後hashは一致した。これは全596位置の網羅やrealtime全graphの期限証明ではない。

90秒の全体予算不足と、終了したcueの非活動枝でAudioParam getterが旧値を保った現象を分離した。観測準備を別の有限予算へ置き、元の4秒・誤差0.002と全mix状態を維持して、既知入力による実バス・master前段の出力を照合した。getter値を目標命令の記録へ置き換えてはいない。参照したBlink mainと実行binaryの厳密なrevision対応は未確認で、無音一般の規則とはしない。

追加したPCM観測の窓は、速いhostで収束前のサンプルを含む反例があるため、audio clockによる1窓＋2quantumのguardを設けた。44.1/48kHz・4状態・8位相のCPU比較では、即読64条件は全て誤差0.002を超え、guard後64条件は全て同基準内（最大0.000331338）だった。C13固定版のguard付きambient-only再確認は104.776秒で完了し、4状態の全窓が条件成立後にあり、実出力・元イベント・解放も通過した。51 offline部分は同じ入力・assertを持つC12の直接証拠を再利用した。guardを含む全targetの180秒通し実行を別途行ったという主張ではない。

## C12の4K連続再生と負荷

MP4のsync sample索引、次表示frameの保持、前方デコードの投入量を修正した。固定C12の333実行入力・103配布ファイルと実際に配信されたコードを開始前後に照合した。3840×2160・24fpsのH.264素材を実Appで使い、0/32位置音源の各6秒ではpresent失敗・自動停止・入力underrunは全て0、各条件156frame・2decoderの解放を確認した。白画像を主とする圧縮素材で、任意の4K動画の複雑度を代表しない。

同じ版の12チャンネルbed・32音源・高品質描画・首振りと小移動では、warm30.530秒＋計測60.928秒、作者Processの22,498区間を採取した。p99は0.941 ms、最大2.152 ms、入力underrunは0。計測内の停止7回は意図したseekに対応し、計測後の手動pause/close1回とは分けた。集計counterの90.928秒には計測開始前の初期status 0.1067秒を含み、窓内の差分は90.8213秒、壁時計は91.458秒だった。連続した無seek条件の時計精度とは扱わない。旧C10では測定内の停止98回中5回がseekに対応し、残る93回が既知の未達だった。

これは実Appの短時間・固定素材の直接証拠で、30分安定性、全入力形式・席・方向の音響出力、退出再訪20回、実機や人間の聴感を合格にするものではない。後続検証は同じ実装・素材・配布閉包へ結び付ける。元の映像readyによる音声停止条件は維持し、その条件を無効化して継続を装わない。

## C8のネイティブ音声負荷

対象は328実行入力、配布103ファイルの固定版です。開始前後の全hashが一致し、実際に配信された7本の元JSも一致しました。観測用PCM recorderを置かない新規ページで、各条件6秒、姿勢メッセージの実更新数とAudioWorklet作者JavaScriptのprocess実行区間を記録しました。

| 条件 | 実姿勢更新Hz | 作者process p99 / 最大 ms |
| --- | ---: | ---: |
| 単独・90Hz要求 | 90.91 | 0.953 / 2.356 |
| 単独・120Hz要求 | 125.00 | 0.920 / 1.085 |
| 並行描画・120Hz要求 | 125.01 | 0.909 / 0.967 |

この範囲の入力underrun、録音器、ブラウザーerrorは0です。抽出したspanは `AudioWorkletProcessor::Process (author script execution)` で、作者process本体の実行時間です。enqueueやport handlerの受信時間、音声グラフ全体のcallback時間とは異なります。実測の低頻度CDP `renderCapacity` は0.0026276–0.3463666で、参照したBlink実装では前回render所要時間/実callback間隔の瞬時比です。百分率として呼ばず、生値と生成元を保存します。21点の疎な標本は、全callbackの期限超過、平均負荷、長時間の欠落ゼロを証明しません。プロトコルの説明と実装の単位の差、使用バイナリと参照sourceの厳密な対応が未確定な点も区別します。

原始記録の識別子は `cinema-browser-coarse8-performance`、観測script SHA256は`782d00b0d4140298c9efd58594262507be0aef56a151f9c7b5d53ff3e7609ce4`、実行入力manifestは`b891a1fc8860479e301da380a1f61b076e56dbb4f81beda7ea0e43645a485ac0`です。上の値をWindows評価機の30分目標や、4K映像を含む最終アプリ性能の達成として扱いません。

### PCM捕捉と内部停止の限界

C8の旧PCM捕捉器は入力sampleへ `value || 0` を使ったため、NaNも0へ置き換わります。保存PCMのnonFinite=0を元のWorklet出力の有限性保証にせず、保存後の連続した0値が元の無音か非有限値かも、この録音だけでは判定しません。今後の捕捉ではundefinedの欠測だけを0とし、NaN・Infinityは保持し、欠測数を別に記録します。録音器を置かなかった上記の処理時間測定、source/dist/配信hash、内部statusと時計の事実は別の証拠として維持します。

C9の標準App更新を元の320×180/24fps素材、960×540/DPR1で各6秒観測すると、0音源と32音源の両方で、再生要求中・非ブロック・非シークにもかかわらず `picture.present=false` の直後に音声を止める内部playing命令を各12回確認しました。playheadの進みは壁時計6.008/6.007秒に対し5.565/5.581秒で、入力underrunは0です。Movieとdecoderの詳細wrapperを外した対照でも停止13/15回、進み5.555/5.483秒対各6.006秒でした。詳細観測器だけで起きた現象とはせず、十分な連続出力の受け入れは未達とします。

この停止は、実際に出せる映像がないとき音を止める同期の契約に沿います。ただし、次に必要な映像frameを先読みcacheから削る経路と、MP4 sync sampleを4byteではなく1byteずつ読む既存の不具合が確認され、個別の修正対象になっています。私用のGPU無効WebCodecs比較で後半・末端・逆行seekが準備できても、軽い6秒固定clockでは旧新ともpresent失敗0だったため、実Appの連続再生改善まで確認したことにはしません。C10の固定版で、非有限値を隠さない捕捉と内部gate・時計・出力を再照合します。物理機器の運用確認へ移す未達ではありません。

## C9への証拠の再利用

C9の音響差分は、初期反射の上限を絶対到達250msから「1m距離丸めと固定alignmentを含む直接到達＋250ms」へ直す既存モジュールと、その回帰試験です。旧R2a/C8には絶対窓が残ります。C9 snapshotのSHA256は`1309fd15927c1a4d335d15e533e9ae4da31686a76cc0026d38c3a2f4d6f5e1bc`です。

100着座＋許可された42飛行の142姿勢では、適格候補が増えても上位48経路の全fieldは不変でした。同じ生成module、連続入力、姿勢、シークと部分chunkで61824出力frame、57履歴、時計・生存期間を照合し、R2aとC9はbit同一でした。この閉じた条件の出力の証拠は維持できます。選別前の候補は増えるため幾何準備の負荷まで同一とはせず、Node成分比較の中央値は1.488→1.580msでした。C8の短いネイティブ性能をC9全アプリの期限合格へ読み替えず、C9実配布版の狭い差分を別に確認します。

既存128sample補正の診断では、C8の実compiled Workletと旧source Workletを同じ中央直接音で駆動し、有意onset5637sample・peak5662sampleが両耳で一致しました。新しいブロック待ちの差は0sample、上映用補正とpeakの差約2.158msは既存値です。これは中央直接音を隔離した診断で、映像表示や物理出力のAV同期の測定ではありません。

## 完成判定へ残す確認

全域の連続巡回、座位・立位・低姿勢と端部、4照明と無映像/白/部分白/色、共有・ローカル上映・モニター、pause/seek・非常点検・席移動・退出再訪、環境音の前後比較、解放の反復、実出力と独立品質・コードレビューを対象版へ結び付けます。数値で既知の不合格を所有者の機器確認へ移しません。

KEMARの60方向と下向き−20°の範囲制約は維持し、座席と高所飛行で物理方向と選択binを記録します。前後上下の実聴取、全帯域の到達・反射・尾部、合成時の位相干渉を係数の二乗和だけで合格にしません。物理HMD・Windows機・OSの実画面共有は、開発受け入れを代替しない所有者の運用確認として分離します。
