# エージェントハーネス

Codex の運用は、アプリで有効な設定と指示に従います。この文書は Lumen 固有の作業記録と検査手順を案内します。文書ごとの責務、更新条件、受け入れ基準は[文書の責務と更新基準](documentation-structure.md)を正本とします。

## 正本と更新先

変更した契約に対応する正本を[文書の責務と更新基準](documentation-structure.md)で確認し、該当ページを更新します。複数の契約に影響する場合は、それぞれの正本を確認し、同じ事実を複数ページへ重ねて書かず、入口から正本へリンクします。

## Issue・PRの記載

### 起票と分割

関連する既存Issueを確認し、同じ成果を扱うIssueがあれば優先して使います。チャットだけの方針提案はIssueを起こす対象にしません。

Issueは独立した成果と合否判定を持つ単位にします。同一成果の調査・実装・テストは同じIssueで追い、独立した成果と受け入れ条件がある場合に限って分けます。現PRの受け入れを妨げる指摘は、別Issueへの切り出しで解除しません。

### Issue本文

[Issueテンプレート](../.github/ISSUE_TEMPLATE/change.md) に、依頼と着手理由、現状と利用者への影響、根拠、期待する成果、対象と対象外、判断、受け入れ条件と確認方法、リスク・未確認事項を記載します。ユーザーの依頼と実装者の判断を分け、事実には出典を、仮説には確認方法を添えます。内部改善では担当者の期待成果と維持する利用者の挙動を明記します。

各受け入れ条件には第三者が合否を判定できる結果と確認方法を示します。判断や範囲を変えた場合は、理由と受け入れ条件への影響をIssueコメントに残し、本文を更新します。

### PR本文

[PRテンプレート](../.github/pull_request_template.md) に主Issue、このPRが扱う受け入れ条件、変更理由と手法、維持する挙動・契約、影響を受ける正本、検証実績と証拠、CI・レビューの状況、未実施・未確認の項目と影響を記載します。各受け入れ条件に確認方法・結果・証拠を対応付けます。

PRは独立してレビュー・検証・取り消しできる単位にします。関連する実装・回帰テスト・影響を受ける正本文書は同じPRに含め、複数PRに分ける場合は各PRの受け入れ範囲を示します。既存Issueに基づく文書変更もそのIssueへ紐づけます。

### 進行段階の確認

1. **作業開始前** 関連する既存Issueを確認し、主Issueを確定します。Issue本文に依頼・判断・根拠・範囲・リスク・受け入れ条件と確認方法がそろってから、ソースコードの変更に着手します。
2. **最初のDraft作成時** ソースコード変更を含むPRは主IssueをリンクしてからDraftを作成します。既存Issueに基づく文書変更もそのIssueへリンクします。PRが扱う受け入れ条件と範囲が定まらなければ、Draft作成を進めません。
3. **Readyへ変更するとき** 最終差分とPR本文を照合し、受け入れ条件ごとの検証実績・結果・証拠、文書への影響、CIとレビューの現時点の状況、未確認事項と受け入れへの影響を記録します。受け入れ条件に対応する証拠が欠けていればDraftで補います。
4. **マージ前** 最新のCI・レビュー結果、未解決の重大な指摘、mergeabilityとIssueの全受け入れ条件を照合します。重大な指摘や必須の確認が残る場合はマージしません。最終履歴・検証結果・全条件を再確認し、すべて満たせば `Closes #番号`、部分対応またはマージ後に受け入れ確認が残る場合は `Refs #番号` を使います。配布などが受け入れに含まれる場合は実際の結果を確認します。

| 対象 | 記録する条件と証拠の例 |
| --- | --- |
| 景観 | 視点・時刻・描画設定をそろえた変更前後の画像 |
| 音響 | 場所・時刻・音量設定をそろえた録音や測定値 |
| 操作 | 起点・ブラウザや入力機器・手順と、ブラウザ試験や手動確認の結果 |

素材を公開できない場合は、確認条件と結果を公開できる範囲で記載します。

## 更新と検証

文書や参照を変更したら `npm run validate:harness` を実行します。[静的検査](../scripts/validate-harness.mjs) は `docs/` 内の現行 Markdown 文書、README とリポジトリ指示、`public/**/ATTRIBUTION.md` のクレジット、既存の計画案内、Skill を確認します。相対リンクと Markdown 見出しアンカー、記載された npm スクリプト、README から現行ページやクレジットへ関連文書を経由して到達できること、Skill frontmatter を検査します。

静的検査の成功は、記述内容の正しさ、利用環境の設定、ブラウザーや OS の実機挙動を証明しません。機能変更に対応する検証は[検証と配布ビルド](verification.md)に従って行い、実施できなかった確認とその影響を記録します。[旧ゲームの計画と進捗](../plans/README.md#旧ゲームの履歴)および[作業計画テンプレート](../plans/TEMPLATE.md)は現在の仕様を定める文書に含めません。
