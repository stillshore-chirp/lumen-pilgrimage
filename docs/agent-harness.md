# エージェントハーネス

Codex の運用は、アプリで有効な設定と指示に従います。この文書は Lumen 固有の業務工程、作業記録、検査手順を案内します。文書ごとの責務、更新条件、受け入れ基準は[文書の責務と更新基準](documentation-structure.md)を正本とします。

## 専門分野の業務工程

本節は、依頼に関係するすべての専門分野と、調査・設計・制作・実装・レビュー・完了判定に自動適用する必須規則です。個別の指示を待たず、求められた用途で成果が成立するまで、必要な調査、設計への反映、制作・実装、実物の検証と修正を続けます。工程の深さと記録量は、依頼された段階、変更規模、利用者への影響、不確実性に合わせます。規模が小さくても、根拠の妥当性、成果への反映、対応する検証の義務は省きません。工数、作業の長さ、実装の容易さを理由に品質や受け入れ条件を引き下げません。

### 現況と関連分野の確定

着手時に、有効な指示、依頼と合意、作業対象の最新状態、現行の[正本](#正本と更新先)、実際の挙動、利用環境を確認します。旧版・過去の設計や記録は差分と経緯の確認に使い、現行仕様との一致を確かめずに制作の根拠にしません。

要求、用途、利用環境、変更の影響、不確実性から、関係する分野と品質を左右する工程を洗い出します。音響、光学・照明、材料、建築、地形・植生、物理、知覚・人間工学、操作、計算性能を例に、対象に必要な分野を追加します。生成・構造から、配置・組合せ・伝達を経て、最終的な知覚と操作に至る範囲を扱います。例えば音響では音の生成と時間・周波数構造、空間内の伝搬、耳への出力と聴感をつなぎ、形状・材料・開口・移動・負荷との相互作用も確認します。

既存の調査や専門書は、出典と参照箇所、適用条件、今回の要件、変更の影響を照合して再利用し、不足する調査だけを追加します。過去の成果も、未確認の部分を今回の基準へ適合済みと宣言しません。

### 原典の調査と判断

設計判断の前に、原著論文、規格本文、公式技術資料、原データなど、根拠とする一次資料の該当箇所を実際に読みます。[専門書](learning/README.md)は体系の理解と原典の探索に使い、判断に使う記述は原典まで確認します。書誌情報、検索結果、要約の収集だけで調査を完了せず、未読の資料を根拠にしません。

資料では、対象、前提、成立範囲、実験・測定方法、数値と単位、近似、限界を確かめます。確認した事実、資料からの推論、実装上の仮定、経験による調整、未確認事項を区別して記録します。判断を左右する不確実性や資料間の相違は、追加の原典、計算、試作、測定で検討します。必要な資料を確認できない場合は、その影響を示し、確認できる資料や別方式を探します。

### 設計・制作への反映と追跡

採用する根拠は、次の対応を既存の設計資料、[Issue・PR](#issueprの記載)、実装・制作物から追える状態にします。新しい記録用文書を一律に増やさず、各[正本の責務](documentation-structure.md)に沿って詳細を置き、他の記録から参照します。

> 要求・問題 → 出典の参照箇所と適用条件 → 原理・モデル・仮定 → 設計値・アルゴリズム・制作方法 → 実装パス・制作物 → 検証条件・結果・制約

出典は版、章・節、ページ、式・図表など、採用した箇所を特定します。数式や専門用語を使う場合は、変数・単位・前提と、それがどの設計値や処理、制作方法に使われたかを示します。近似や簡略化は、採用理由、適用範囲、品質と性能への影響を説明し、要求を満たすことを検証します。

基本設計では全体構成と実現方法を決め、成立性を左右する点を図、計算、試作などで確かめます。詳細設計は、寸法入りの平面・断面、材質・照明仕様、音源・聴取点の配置、操作と状態など、制作と検証に使える形にします。分野がまたがる部分は、座標、開口、時間、利用条件など共通の前提で突き合わせます。

独自のモデル、生成技術、アルゴリズムが要求を満たすために有効なら、必要な研究開発と試作を行います。既存方式や外部素材を使う場合も、対象への適合、調整、制約、組み込み方を設計します。制作・実装後は設計と実態を照合し、不一致があれば原因を調べ、該当する設計または成果物を修正して再検証します。

### 外部素材と技術方式の採用

録音、画像、3Dモデル、測定データ、ライブラリ、既製アセット、学術資料の文章・図表・コードなどを採用する前に、出典、提供者・権利者、ライセンスと条件を一次情報で確認します。予定する利用、改変、配布との適合を調べ、必要な表示、改変物の扱い、再配布・同梱の義務を成果物と記録へ反映します。技術方式は、採用する方式・用途・実施地域に関係する特許などの権利と利用条件について必要な一次資料を確認し、該当し得る請求項、権利の状態、予定用途との適合を確かめます。

素材・方式は、科学・技術上の妥当性、完成品質、機能、性能、権利、保守、再現性、検証可能性に基づいて比較・選定します。条件を実際に守れるか、管理負担と配布形態が整合するかを代替案と併せて評価します。具体的な権利上の懸念は調査で解消するか、懸念の少ない素材・方式へ置き換えます。利用できる根拠が不明なまま採用しません。自作、生成、無料という分類だけで品質や権利上の安全性を断定せず、依頼にない全自作化や特定ライセンスの一律排除を追加要件にしません。

これらの条件を満たす素材・方式の調査、比較、採用、加工、組み込みは、依頼の範囲で所有者の事前承認を求めず自律的に進めます。第三者から必要な許諾を得る義務と、有効な権限・ツールの境界は守ります。外部採用後も、本節の調査、設計、制作・実装、実物検証と修正を継続します。判断の根拠は設計資料やIssueへ、素材単位の出典と配布条件は該当する `ATTRIBUTION.md` へ記録します。取得・加工・取り込みと再現の手順は[素材の所在と再現手順](assets.md)に従います。

外部音声の採用原則、第三者権利・倫理、CC0の扱い、14項目の台帳は[音声採用基準](assets.md#外部音声の採用基準)を正本とします。探索開始、Ready・レビュー、完了の各段階で台帳・配布物・実使用・品質評価を照合します。音声の権利・倫理・公開配布に関する必須条件が未解決なら公開・配布へ進めません。研究用比較、技術上の採用、完成品質の合否を区別し、必須確認が未実施の成果を完了扱いしません。候補の不採用や一部の未確認があっても、独立して進められる工程は継続します。

### 受け入れと実物検証

制作前に、用途と利用環境に沿う受け入れ条件、確認方法、判定基準を定めます。科学・技術上の妥当性、知覚される完成品質、機能、性能、権利、保守など、要求に必要な軸を含めます。条件ごとに対象、入力、機器・環境、方法、期待結果・判定基準、実結果と証拠、残る制約を記録します。

見た目、音質、空間の成立、操作感は、対象となる成果物を直接観察・試聴・操作・測定して判定します。計算、シミュレーション、模擬入力、実測、実機確認、知覚評価は、それぞれの確認範囲を区別します。ビルド、型、静的検査、単体テストの成功だけで体験品質や実機性能を合格にしません。不合格なら原因を特定し、修正して同じ条件で再検証します。成果に合わせて受け入れ条件を事後に引き下げたり、必須確認を任意へ変えたり、未実施を実施済みとして扱ったりしません。条件の変更が必要なときは、理由と利用への影響を示して合意を得るまで元の条件を維持します。

機器、データ、権限、観測手段が不足する場合は、可能な代替確認と限界を記録し、必須の未検証条件を残します。根拠のない「問題なし」「同等」「完了」と判定しません。一部が阻害されても独立して進められる工程を継続し、真に進められない工程は、達成済みの成果、残作業、再開・完了に必要な条件を具体的に報告します。[検証手順](verification.md)と[進行段階の確認](#進行段階の確認)に従い、必要な証拠がそろってから完了を判定します。

依頼が調査までなら根拠、判断、残る不確実性が追える調査結果、設計までなら次工程で制作できる図面・仕様を、その段階の成果条件で判定します。依頼に制作・実装・検証が含まれる場合は、それらを完了する責務を調査や設計の提出で免除しません。小さな不具合修正も、再現条件、根拠、変更箇所と理由、成果物上の修正確認を揃えます。

### ワールドの初回提示の品質基準

新設・大幅改修するワールドでは、[専門分野の業務工程](#専門分野の業務工程)に加えて以下を必須とし、完成した[商業アトリウムの実装事例](learning/atrium-case.md#商業アトリウムの実装で確かめたこと)を作り込みの水準の参照とします。プレイ用の実装版は、依頼、参照資料、合意済みの仕様から定まる受け入れ条件をすべて満たした状態で提示します。着手時に把握できた条件について、提示後の大きな手戻りはゼロを目標とします。

以下の工程を[進行段階の確認](#進行段階の確認)へ結び付け、参照資料、解析、設計、モデル、実装、検証の対象版と証拠を対応付けます。既存の実装事例や過去の検査結果は参考に使い、今回の基準で未確認のワールドを適合済みとは判定しません。

既存ワールドの小さな変更でも、影響する設計、参照画像の領域、可視包絡と実出力を再照合します。検証範囲は変更の影響に基づいて定め、改修規模の分類だけで関係する不合格や未確認を免除しません。

#### 参考画像の段階的解析

参考画像から制作する場合は、次の順序で解析し、各段階の結果を設計正本から追える状態にします。画像内で確認できる事実、寸法や奥行きなどの推定、画像外を補う制作上の仮定、未確認事項を区別し、判断の確度と確認方法を添えます。

1. **原画像と撮影条件を特定する** 画像ID、取得元・原本の場所と版、原寸の幅・高さと解像度、縦横比、既知の画角・撮影条件を記録します。画角などが不明な場合は不明とし、推定値には根拠と不確実性を添えます。縮小表示や切り抜きだけから全体を判断せず、利用可能な原寸画像を確認します。
2. **全体の関係を観察する** 全景で構図と視線、透視関係・消失点・地平線、物体間の相対寸法、近景・中景・遠景、地形・建築・水・植生、光と影・反射、空間の用途と接続を読み取ります。画面端で続く輪郭、遮蔽、反射など画像外の構造を推定する手掛かりも記録します。この全体観察を、後続の分割解析と照合する基準にします。
3. **重複する規則グリッドで全面を調べる** 行列状の領域に分割し、隣接領域を重ねて境界をまたぐ構造も確認します。分割数、領域の大きさと重複幅は、画像の解像度、物体と細部の密度、読み取る対象の大きさから決め、その根拠を記録します。全画面を覆う領域IDと原画像上の座標を残し、各領域の形、材質、接触、支持、遮蔽、照明を観察します。
4. **対象別に周辺を含む切り抜きを調べる** 重要な物体や接合部は、規則グリッドに加えて対象別の切り抜きで確認します。画面内で小さくても、支持、開口、境界、水際、光源など成立性を左右する対象を含めます。周辺との位置・支持・遮蔽の関係が読める範囲を確保し、対象ID、領域ID、切り抜きの原画像座標を対応付けます。
5. **全体座標と3D設計へ再統合する** 分割領域と対象別の結果を原画像全体の座標へ戻し、同じ物体には共通のIDを使います。特徴、輪郭、支持と接触、前後の遮蔽、寸法推定、照明、材質の連続を、撮影視点とワールドの共通3D座標へ対応付けます。領域間や画像間で食い違う推定は、根拠、採用した解釈、残る不確実性を示して設計へ反映します。

#### ワールド全域の先行設計

詳細制作の前に、世界の用途、規模、利用環境、関係する専門分野を確定し、どの位置で何が見え、何がどの方向から聞こえ、移動・振り返り・滞在で知覚と操作がどう変わるかを設計します。採用した原典と適用条件を、形状・素材・光・音の設計値、制作方法、受け入れ条件へ対応付けます。情緒や景観の狙いも、この体験と結び付けます。 [景観の奥行きと情緒](learning/vr-evaluation.md#景観の奥行きと情緒)

制作範囲は、許可するすべての移動と姿勢から見える範囲の総体を、可視包絡として求めて決めます。窓・開口・反射、位置の変化による視差、高低差、上下の視線、地平線まで含め、必要な奥行きと連続する構造を設計します。範囲を一律の距離で区切らず、移動範囲の外側も、そこから見聞きする地形・建築・環境が成立するところまで扱います。参考画像の左右、背後、上下、遮蔽物の裏にもつながる世界を設計し、画像に写る面だけを制作範囲にしません。

設計正本には、制作と検証に使う寸法入りの平面・断面、地勢・水系と地盤、建築の内外、床裏・屋根裏、支持構造、動線と移動境界、植生、遠景、光と音、時刻・天候など対象となる環境状態を記します。主構造は共通の座標・寸法定義に置き、描画される支持面と接地・衝突を一致させます。岸と水面、斜面と地盤、建築と地形、植生と地面の接続、開口や材質を介した光・音の関係を分野間で照合します。移動の端は、その空間にふさわしい目に見える境界で閉じます。

時間・自然・環境の変化は、世界の用途と受け入れ条件に必要な対象を選び、関連分野の原理からモデル化します。太陽・月・星、雲と大気、水、風と植生、生物の生息条件と行動、設備の動作、光・音の伝搬、プレイヤーの作用と再訪時の状態から、必要なものの入力・状態・変化・相互作用を定めます。地形、開口、支持・衝突、共通の時間と環境状態と整合させ、切替と時間経過の両方を設計します。静かに滞在する用途では、生物や設備の活動頻度、音や動きの発生間隔と強さも設計します。対象外の現象を一律に追加せず、モデルの採否と簡略化の根拠を記します。

資料だけで決められない構造、画像外の接続、規模などが成立性を左右する場合は、複数案を比較し、採用理由と補完した仮定、寸法の根拠、品質・性能への影響を残します。未確定部分を詳細制作の都合だけで埋めず、次の粗い3Dモデルと設計レビューで確かめます。

#### 粗い3Dモデルと独立設計レビュー

詳細制作へ進む前に、先行設計に基づき、全域を移動・観察できる実行可能な粗い3Dモデルを必ず制作します。平面・断面図とモデルを対応付け、実際に起動して、通常の移動と視点操作で次の範囲を確認します。図面、静止画、実行していない試作を、この実動確認の代替にしません。

- 開始点と主な着地点、参考画像に対応する方向、左右90度、背面180度、上下の視線。
- 主な視点から空間や施設の用途を読み取れるか、重要な対象が実際に見えるか、主要な光源・音源の位置と見聞きする方向が設計に合うか。
- 許可する立位・座位・低い姿勢、移動経路とその端、窓・開口や枠・柱・袖壁・手すりの際からの斜めのぞき。
- 移動中に現れる遮蔽物の裏、足元と支持構造、建築と地形の接点、水際、近景・中景・遠景から地平線までの重なり。

制作担当から独立した専門横断の設計レビューも必須とします。担当人数を固定せず、変更のリスクと不確実性から、建築・構造、地形・水系、植生、光学・照明、音響、操作・知覚、性能など必要な専門視点を確保します。レビュー対象の設計・モデルの版、担当と確認分野、実動確認の条件と証拠、指摘・対応・再確認結果を記録します。構造、支持、接続、可視包絡、動線に加え、用途の判読、重要対象の可視性、光・音の配置や知覚に関わる重大な問題を設計とモデルで解消し、再確認してから詳細制作へ進みます。

#### 制作候補と最終版の全方向検証

制作候補のレビュー時と初回提示前の最終ビルドで、[段階的解析](#参考画像の段階的解析)と[全域設計](#ワールド全域の先行設計)を成果物へ照合します。参考画像は全体画像、同じ規則グリッド領域、同じ対象別領域で再比較します。実際のカメラの画角・位置・向き、内部描画解像度、DPR、表示寸法・縦横比、時刻と光の方向・質、環境・操作状態を固定して記録し、画像との撮影条件の差や推定も明らかにします。

既定の画質と通常の操作で、全移動範囲を実際に巡回します。開始点から経路、着地点、移動範囲の端、窓や開口まで連続して動き、360度と上下を見回し、境界の際からのぞき、遮蔽物の裏と支持面を確認します。対象となる時間・環境状態を切り替え、同じ場所へ再訪して、地形・水・建築・植生・遠景、光・反射・音・生き物や操作状態の連続を確かめます。固定視点の画像だけで巡回を置き換えません。 [検証手順](verification.md)

直接観察・試聴・操作に、寸法と幾何の照合、接触・支持判定、レイキャスト、参照視点への投影など対象に適する測定を組み合わせます。構造の欠落、浮遊、水際の切断、必要な奥行きの不足、移動中の物体の不自然な出没、環境の不連続は不合格とします。制作境界の露出、未制作部分への進入、意図しない隙間・反復模様、反射や音の経路の不整合も修正対象です。静的検査や単体テストの成功を、視覚・音響・操作品質の証拠に置き換えません。

制作候補と最終版の判定では、制作担当から独立した実出力の品質評価と、実装担当から独立した変更コードのレビューをそれぞれ行います。画像・音・操作の実出力、設計との一致、実装上の妥当性を別々に評価し、コードレビューだけで画像などの完成品質を合格にしません。必要な専門視点はリスクに応じて確保し、人数は固定しません。それぞれの担当、対象版、確認条件・証拠、指摘と対応、最終差分との対応を記録し、適用できる設計レビューも併せて照合します。

不整合の原因は設計正本まで戻って確かめ、必要な寸法図、生成処理、実装、検証条件を同期して修正します。同じ経路・視点・環境条件で再検証し、関連する別方向や境界への影響も確認します。最適化では世界の構造定義と描画対象の選択を分離し、LOD・カリングの切替や継ぎ目、影・反射・音・生き物の状態が、移動と環境切替を通して連続することを確認します。性能が要求条件に含まれる場合は、対象環境で負荷の高い場面と切替時の実際のGPU負荷・メモリ・フレーム時間・初期化と更新時間を検証します。確認する環境・機種と実機の扱いは、依頼で合意した範囲に従います。自動検査は[変更影響による選択](verification.md#変更影響によるゲート選択)に従い、無関係なワールドの試験を一律追加しません。

対象版と条件をそろえた比較画像、巡回経路、録音・計測値、操作結果、指摘と再検証の証拠を、設計正本から既存のIssue・PRへ参照でつなぎます。見た目や動作の確認と情緒の評価を分け、情緒については専門家の所見と利用者から測った反応を区別します。 [PRの確認結果と証拠](#pr本文)

## 正本と更新先

変更した契約に対応する正本を[文書の責務と更新基準](documentation-structure.md)で確認し、該当ページを更新します。複数の契約に影響する場合は、それぞれの正本を確認し、同じ事実を複数ページへ重ねて書かず、入口から正本へリンクします。

### 専門書の加筆と保守

ワールドの調査・設計・実装・検証で、他の空間にも応用できる知見を確認したら、[専門書「歩ける空間の設計」](learning/README.md)の該当章に加筆します。原理、適用条件、設計判断の理由を章の流れに沿って説明し、一次資料の該当箇所や検証記録を参照できるようにします。関連する設計や実装をPRで反映する場合は、章の更新も同じPRに含めます。個々のワールドの座標、仕上げ、操作は各ワールドの正本に記録し、必要に応じて章から参照します。

専門書を設計判断に使うときは、参照した箇所の出典、適用条件、計算や図版の前提を照合します。資料の改訂、リンク切れ、誤りを見つけたときは、該当箇所を訂正し、同じ前提を使う関連章と図版にも反映します。確認した事実、資料からの推定、計算例で仮定した値は本文で区別します。

専門書の読解・加筆にも[原典の調査と判断](#原典の調査と判断)を適用します。章や引用の追加だけで調査完了とせず、成果の判断に使った知見は[設計・制作への反映と追跡](#設計制作への反映と追跡)へ結び付けます。変更した計算例は再計算し、本文と図の数値・単位・用語が一致すること、数式と図版が正しく表示されることを確認します。章の追加や移動に合わせて目次と関連章の参照を更新し、[更新と検証](#更新と検証)の静的検査を実行します。

## Issue・PRの記載

### 起票と分割

関連する既存Issueを確認し、同じ成果を扱うIssueがあれば優先して使います。チャットだけの方針提案はIssueを起こす対象にしません。

Issueは独立した成果と合否判定を持つ単位にします。同一成果の調査・実装・テストは同じIssueで追い、独立した成果と受け入れ条件がある場合に限って分けます。現PRの受け入れを妨げる指摘は、別Issueへの切り出しで解除しません。

### Issue本文

[Issueテンプレート](../.github/ISSUE_TEMPLATE/change.md) に、依頼と着手理由、現状と利用者への影響、根拠、期待する成果、対象と対象外、判断、受け入れ条件と確認方法、リスク・未確認事項を記載します。ユーザーの依頼と実装者の判断を分け、事実には出典を、仮説には確認方法を添えます。内部改善では担当者の期待成果と維持する利用者の挙動を明記します。

各受け入れ条件には第三者が合否を判定できる結果と確認方法を示します。[現況と関連分野](#現況と関連分野の確定)、調査・設計の根拠、[実物検証の条件](#受け入れと実物検証)は、該当する設計正本と参照し合う形で記録します。依頼された範囲で必要な判断を自ら行い、問題の解消と検証を続け、求められた成果を届けるまで進めます。

### PR本文

[PRテンプレート](../.github/pull_request_template.md) に主Issue、このPRが扱う受け入れ条件、変更理由と手法、維持する挙動・契約、影響を受ける正本、検証実績と証拠、CI・レビューの状況、未実施・未確認の項目と影響を記載します。このPRで完了させる受け入れ条件に確認方法・結果・証拠を対応付けます。[根拠から成果への対応](#設計制作への反映と追跡)と[採用条件の確認](#外部素材と技術方式の採用)は、正本と成果物の参照から確かめられるようにします。

PRは独立してレビュー・検証・取り消しできる単位にします。関連する実装・回帰テスト・影響を受ける正本文書は同じPRに含め、複数PRに分ける場合は各PRの受け入れ範囲を示します。既存Issueに基づく文書変更もそのIssueへ紐づけます。

### 進行段階の確認

1. **作業開始前** 最新状態と有効な指示・正本、関連する既存Issueを確認し、主Issueを確定します。Issue本文に依頼・判断・根拠・範囲・リスク・受け入れ条件と確認方法がそろってから、ソースコードの変更に着手します。関係する専門分野、調査済みの範囲と不足、分野間の共通前提、ワールドの新設・大幅改修に当たるかを特定します。参考画像を使う場合は画像IDと原本・撮影条件、不明点を確かめ、[段階的解析](#参考画像の段階的解析)の対象を定めます。
2. **設計開始前** 設計判断に必要な原典と不確実性を確かめます。参考画像がある場合は全体・規則グリッド・対象別の解析と全体座標への再統合を行い、事実・推定・制作上の仮定を設計正本へ対応付けます。判断に必要な資料や解析が欠けていれば、その判断を確定せず不足を補います。
3. **詳細制作前** 新設・大幅改修ワールドは、[全域の先行設計](#ワールド全域の先行設計)、[粗い3Dモデルの実動確認と独立設計レビュー](#粗い3dモデルと独立設計レビュー)の対象版・証拠・指摘対応をそろえます。設計範囲、支持・接続、可視包絡、移動境界、用途・知覚に重大な未解決がある場合、またはモデルの実動確認や独立レビューが未実施の場合は詳細制作へ進みません。
4. **最初のDraft作成時** ソースコード変更を含むPRは主IssueをリンクしてからDraftを作成します。既存Issueに基づく文書変更もそのIssueへリンクします。PRが扱う受け入れ条件と範囲が定まらなければ、Draft作成を進めません。Draftの作成順序によって、設計や詳細制作の前提確認を免除しません。
5. **制作候補のレビュー時** 新設・大幅改修ワールドは、[全方向検証](#制作候補と最終版の全方向検証)の比較条件、画像領域、実巡回、測定と指摘・再検証を確認し、独立した実出力の品質評価とコードレビューをそれぞれ記録します。証拠が欠ける範囲や不合格を、代表画像や自動テストだけで合格にせず、未達として修正を続けます。候補に不合格がある状態を、最終版の受け入れ完了と扱いません。
6. **Readyへ変更するとき** 最終差分とPR本文を照合し、このPRで完了させる受け入れ条件の検証実績・結果・証拠、文書への影響、CIとレビューの現時点の状況を記録します。調査の適用範囲、設計への反映、実装・制作物、実物検証、採用した素材・方式の利用条件を対応付けて確認します。新設・大幅改修ワールドでは、最終ビルドの全方向検証、独立した品質評価とコードレビュー、設計・モデルからの変更を照合します。検証では[変更影響による選択](verification.md#変更影響によるゲート選択)の比較元・入力閉包・選択/非対象理由・実行結果を照合し、無関係な検査を定常実行しません。選択範囲にない新規の必須条件は直接評価を追加します。必要な証拠が欠けていればDraftで補います。マージ後にしか確認できない条件は、その理由・確認方法・受け入れへの影響を記録し、Issueに未完了の条件として残します。機器などが不足するだけの確認を、マージ後にしか確認できない条件と扱いません。
7. **マージ前** 最新のCI・レビュー結果、未解決の重大な指摘、mergeabilityと、マージ時点で必要な専門工程・実物検証の証拠を照合します。重大な指摘や必要な確認が残る場合はマージしません。Issueの全条件は、最終履歴・検証結果と併せて `Closes` / `Refs` の判定時に照合します。すべて満たせば `Closes #番号`、部分対応またはマージ後に受け入れ確認が残る場合は `Refs #番号` を使います。
8. **完了報告・Issueのclose時** 合意済みの全条件を、実際の成果物と条件ごとの証拠で判定します。配布などが受け入れに含まれる場合は実際の結果まで確認します。新設・大幅改修ワールドは、最終版の版・条件・全方向検証と指摘解消を照合し、過去版や過去事例で未検証の範囲を埋めません。必須の未実施・未確認があれば完了とせず、達成済みの成果、残件、阻害要因、次に必要な条件を記録します。

チェック欄の充足だけで段階を完了にしません。各段階は、対象とする資料・設計・モデル・成果物の版、証拠への参照、実施条件と結果、未達・未確認と影響を記録して判定します。レビューでは、根拠の妥当性・適用、設計と成果物の一致、検証の方法・結果・制約を照合します。形式の検査と専門判断、ブラウザー上の出力と実機の知覚・性能は、それぞれの証拠が示す範囲で判定します。

| 対象 | 記録する条件と証拠の例 |
| --- | --- |
| 景観 | 視点・時刻・描画設定をそろえた変更前後の画像 |
| ワールド全域 | 画像・領域・対象IDと3D座標の対応、全域設計と実動モデルの版、独立設計レビュー、固定条件の領域比較と連続巡回・再検証の証拠 |
| 音響 | 場所・時刻・音量設定をそろえた録音や測定値 |
| 操作 | 起点・ブラウザや入力機器・手順と、ブラウザ試験や手動確認の結果 |

素材を公開できない場合は、確認条件と結果を公開できる範囲で記載します。

## 更新と検証

文書や参照を変更したら `npm run validate:harness` を実行します。[静的検査](../scripts/validate-harness.mjs) は `docs/` 内の現行 Markdown 文書、README とリポジトリ指示、`public/**/ATTRIBUTION.md` のクレジット、既存の計画案内、[Issue](../.github/ISSUE_TEMPLATE/change.md)・[PR](../.github/pull_request_template.md)・[作業計画](../plans/TEMPLATE.md)の維持対象テンプレート、Skill を確認します。相対リンクと Markdown 見出しアンカー、記載された npm スクリプト、README から現行ページ・クレジット・維持対象テンプレートへ関連文書を経由して到達できること、Skill frontmatter を検査します。入口・品質基準の節・テンプレートが必須工程へ接続する工程参照契約も検査します。

静的検査が機械判定するのは形式と参照の整合であり、実際の工程実施や完成品質を認定しません。調査の妥当性、原典の理解、根拠の設計・実装への反映、権利条件の適合、完成品質は、[専門分野の業務工程](#専門分野の業務工程)の証拠と対応するレビューで確認します。機能変更に対応する検証は[検証と配布ビルド](verification.md)に従って行い、利用環境の設定、ブラウザーや OS の実機挙動も確認範囲を区別します。実施できなかった必須確認とその影響は未検証として残します。[旧ゲームの計画と進捗](../plans/README.md#旧ゲームの履歴)は過去の記録です。[作業計画テンプレート](../plans/TEMPLATE.md)は現行の記録様式であり、仕様の正本の代わりにはしません。
