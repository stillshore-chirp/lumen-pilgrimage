# エージェントハーネス

Codex の運用は、アプリで有効な設定と指示に従います。この文書は Lumen 固有の業務工程、作業記録、検査手順を案内します。文書ごとの責務、更新条件、受け入れ基準は[文書の責務と更新基準](documentation-structure.md)を正本とします。

## 専門分野の業務工程

着手時に、依頼の目的と成果物の用途を確認し、必要な専門分野と工程を選びます。工程の深さは、依頼された段階と利用者への影響、設計上の不確実さに合わせます。

1. **現況調査と要件整理** 参照資料、現行の仕様と実際の挙動、対象環境を確認します。専門的な判断に必要な学術調査を設計や実装の前に行います。原著論文、研究機関の技術報告、規格の本文など、判断に関わる一次資料の該当箇所を読み、対象や測定条件、知見を適用できる範囲を確かめます。観察した事実、資料からの推定、制作上の仮定を明示し、用途と制約を合否が分かる条件へ落とし込みます。
2. **基本設計と詳細設計** 基本設計で全体構成と実現方法を決め、成立性を左右する点は図、計算、試作などで早めに確かめます。案の選択が成果を左右するときは、採用した案と理由を記します。詳細設計は、寸法入りの平面・断面、材質・照明仕様、音源・聴取点の配置、操作と状態の仕様など、作業者が制作と検証に使える形にします。分野がまたがる部分は、座標・開口・利用条件など共通の前提で突き合わせます。
3. **制作と検証** 設計を実装・制作に反映し、実際の成果物を利用条件に沿って確認します。図面・仕様と動作や見え方に食い違いがあれば、原因を調べ、該当する設計または制作物を直して再検証します。判断と確認結果は、関連する[正本](#正本と更新先)や既存の[Issue・PR](#issueprの記載)に記録します。

採用した知見は、判断の根拠となる出典の箇所と、設計値、配置、素材、実装方式、受け入れ条件などにどう反映したかを、既存の設計資料やIssueに記します。制作・検証を含む依頼では、成果物と検証条件を照合して反映を確認します。

学術資料の文章・図表・コード・データを引用・転用・配布するときは、使い方に応じた著作権、ライセンス、提供条件を採用前に確認します。資料から技術方式を実装に採るときは、実施する地域で関係する特許を調べ、該当し得る請求項と権利の状態を確かめます。利用できる根拠を確認し、必要な許諾を得てから採用します。判断の根拠は設計資料やIssueに、素材の出典と利用条件は該当するクレジットに記録します。 [文化庁・他人の著作物の利用](https://www.bunka.go.jp/seisaku/chosakuken/seidokaisetsu/chosakukensha_fumei/) · [INPIT・特許情報の検索と権利状態](https://www.inpit.go.jp/j-platpat_info/index.html) · [WIPO・特許の地域と許諾](https://www.wipo.int/en/web/patents/faq_patents)

調査のみの依頼では、根拠と判断、残る不確実さが追える調査結果をまとめます。設計までの依頼では、次の工程で制作できる精度の図面や仕様をまとめます。小さな不具合修正では、再現条件、変更箇所とその理由、修正後の確認を押さえます。

### ワールドの初回提示の品質基準

新設・大幅改修するワールドでは、完成した[商業アトリウムの実装事例](learning/atrium-case.md#商業アトリウムの実装で確かめたこと)を作り込みの水準の参照とします。最初にプレイ用の実装版を提示する前に、依頼範囲の主要な受け入れ条件をすべて満たします。着手時に把握できた条件について、提示後の大きな手戻りはゼロを目標とします。

1. **体験を設計する** どの位置で何が見え、何がどの方向から聞こえ、歩く・振り返る・留まると見聞きするものや感じ方がどう変わるかを決めます。採用した一次資料の該当箇所と知見の適用条件を、形状・素材・光・音の設計と受け入れ条件に対応付け、設計資料やIssueに記します。写真を使う場合は、部材の位置・比率・輪郭・重なりを照合する視点を決めます。資料から確定できない寸法や音には、設計上の前提と確認方法を添えます。 [景観の奥行きと情緒](learning/vr-evaluation.md#景観の奥行きと情緒)
2. **詳細仕上げ前に形を確かめる** 歩ける限界を定め、そこへ至る経路と端から見える範囲を、平面・断面図または試作で照合します。窓枠・柱・袖壁・手すりの際で斜めからのぞき、下を見て、振り返る視線まで取り、足元の支持、地形と水や建築との接点、近景・中景・遠景の重なりを確認します。参照画像の外にも壁・床・天井の納まりと仕上げをつなぎます。移動の端は空間にふさわしい目に見える境界で閉じ、衝突と足元の支持を描画と一致させます。
3. **提示前に最終ビルドを巡回する** 既定の画質と通常の操作で、開始点から主な着地点、窓や移動範囲の端まで歩き、前後左右と上下を見回します。途中で遮蔽物の陰から見え始める箇所も確認します。参照画像は対応する視点で照合し、参照画像の画面外は設計した素材・照明・奥行きと照合します。形の途切れ、制作境界の露出や未制作部分への進入、足元の支持の欠落、意図しない隙間や継ぎ目の反復模様、反射や音の経路の不整合を確かめます。主要な破綻は初回提示前に直します。同じ経路と条件で再確認し、視点を変えても場所のつながりが保たれることを合格条件にします。描画負荷が条件に含まれる場合は負荷の高い場面も確認します。確認する環境・機種と実機の扱いは、依頼で合意した範囲に従います。 [検証手順](verification.md)

視点位置・向き・画角、時刻、描画設定をそろえた変更前後の画像と、巡回経路、必要な録音・計測値や操作結果を既存のIssue・PRに記録します。見た目や動作の確認と情緒の評価を分け、情緒については専門家の所見と利用者から測った反応を区別します。 [PRの確認結果と証拠](#pr本文)

## 正本と更新先

変更した契約に対応する正本を[文書の責務と更新基準](documentation-structure.md)で確認し、該当ページを更新します。複数の契約に影響する場合は、それぞれの正本を確認し、同じ事実を複数ページへ重ねて書かず、入口から正本へリンクします。

### 専門書の加筆と保守

ワールドの調査・設計・実装・検証で、他の空間にも応用できる知見を確認したら、[専門書「歩ける空間の設計」](learning/README.md)の該当章に加筆します。原理、適用条件、設計判断の理由を章の流れに沿って説明し、一次資料の該当箇所や検証記録を参照できるようにします。関連する設計や実装をPRで反映する場合は、章の更新も同じPRに含めます。個々のワールドの座標、仕上げ、操作は各ワールドの正本に記録し、必要に応じて章から参照します。

専門書を設計判断に使うときは、参照した箇所の出典、適用条件、計算や図版の前提を照合します。資料の改訂、リンク切れ、誤りを見つけたときは、該当箇所を訂正し、同じ前提を使う関連章と図版にも反映します。確認した事実、資料からの推定、計算例で仮定した値は本文で区別します。

変更した計算例は再計算し、本文と図の数値・単位・用語が一致すること、数式と図版が正しく表示されることを確認します。章の追加や移動に合わせて目次と関連章の参照を更新し、[更新と検証](#更新と検証)の静的検査を実行します。

## Issue・PRの記載

### 起票と分割

関連する既存Issueを確認し、同じ成果を扱うIssueがあれば優先して使います。チャットだけの方針提案はIssueを起こす対象にしません。

Issueは独立した成果と合否判定を持つ単位にします。同一成果の調査・実装・テストは同じIssueで追い、独立した成果と受け入れ条件がある場合に限って分けます。現PRの受け入れを妨げる指摘は、別Issueへの切り出しで解除しません。

### Issue本文

[Issueテンプレート](../.github/ISSUE_TEMPLATE/change.md) に、依頼と着手理由、現状と利用者への影響、根拠、期待する成果、対象と対象外、判断、受け入れ条件と確認方法、リスク・未確認事項を記載します。ユーザーの依頼と実装者の判断を分け、事実には出典を、仮説には確認方法を添えます。内部改善では担当者の期待成果と維持する利用者の挙動を明記します。

各受け入れ条件には第三者が合否を判定できる結果と確認方法を示します。判断や範囲を変えた場合は、理由と受け入れ条件への影響をIssueコメントに残し、本文を更新します。

### PR本文

[PRテンプレート](../.github/pull_request_template.md) に主Issue、このPRが扱う受け入れ条件、変更理由と手法、維持する挙動・契約、影響を受ける正本、検証実績と証拠、CI・レビューの状況、未実施・未確認の項目と影響を記載します。このPRで完了させる受け入れ条件に確認方法・結果・証拠を対応付けます。

PRは独立してレビュー・検証・取り消しできる単位にします。関連する実装・回帰テスト・影響を受ける正本文書は同じPRに含め、複数PRに分ける場合は各PRの受け入れ範囲を示します。既存Issueに基づく文書変更もそのIssueへ紐づけます。

### 進行段階の確認

1. **作業開始前** 関連する既存Issueを確認し、主Issueを確定します。Issue本文に依頼・判断・根拠・範囲・リスク・受け入れ条件と確認方法がそろってから、ソースコードの変更に着手します。
2. **最初のDraft作成時** ソースコード変更を含むPRは主IssueをリンクしてからDraftを作成します。既存Issueに基づく文書変更もそのIssueへリンクします。PRが扱う受け入れ条件と範囲が定まらなければ、Draft作成を進めません。
3. **Readyへ変更するとき** 最終差分とPR本文を照合し、このPRで完了させる受け入れ条件の検証実績・結果・証拠、文書への影響、CIとレビューの現時点の状況を記録します。これらの条件に対応する証拠が欠けていればDraftで補います。マージ後にしか確認できない条件は、その理由・確認方法・受け入れへの影響を記録し、Issueに未完了の条件として残します。
4. **マージ前** 最新のCI・レビュー結果、未解決の重大な指摘、mergeabilityと、マージ時点で必要な確認を照合します。重大な指摘や必要な確認が残る場合はマージしません。Issueの全条件は、最終履歴・検証結果と併せて `Closes` / `Refs` の判定時に照合します。すべて満たせば `Closes #番号`、部分対応またはマージ後に受け入れ確認が残る場合は `Refs #番号` を使います。配布などが受け入れに含まれる場合は実際の結果を確認します。

| 対象 | 記録する条件と証拠の例 |
| --- | --- |
| 景観 | 視点・時刻・描画設定をそろえた変更前後の画像 |
| 音響 | 場所・時刻・音量設定をそろえた録音や測定値 |
| 操作 | 起点・ブラウザや入力機器・手順と、ブラウザ試験や手動確認の結果 |

素材を公開できない場合は、確認条件と結果を公開できる範囲で記載します。

## 更新と検証

文書や参照を変更したら `npm run validate:harness` を実行します。[静的検査](../scripts/validate-harness.mjs) は `docs/` 内の現行 Markdown 文書、README とリポジトリ指示、`public/**/ATTRIBUTION.md` のクレジット、既存の計画案内、Skill を確認します。相対リンクと Markdown 見出しアンカー、記載された npm スクリプト、README から現行ページやクレジットへ関連文書を経由して到達できること、Skill frontmatter を検査します。

静的検査の成功は、記述内容の正しさ、利用環境の設定、ブラウザーや OS の実機挙動を証明しません。機能変更に対応する検証は[検証と配布ビルド](verification.md)に従って行い、実施できなかった確認とその影響を記録します。[旧ゲームの計画と進捗](../plans/README.md#旧ゲームの履歴)および[作業計画テンプレート](../plans/TEMPLATE.md)は現在の仕様を定める文書に含めません。
