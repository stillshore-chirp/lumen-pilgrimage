# コーディング規約

実装とレビューで守る契約、および場面に応じて選ぶ設計判断を定めます。機能ごとの詳しい仕様は[アーキテクチャ](architecture.md)、[ワールド案内](worlds.md)、[仮想モニター仕様](monitor.md)、各設計資料に記載します。必須の安全条件と検証ゲートは [AGENTS.md](../AGENTS.md) を参照してください。

規約は新規コードと、変更が触れる契約・責務の境界に適用します。既存実装への適用範囲は、変更する入出力、状態遷移、資源の所有権と寿命に沿って決めます。

## 必須契約

### 利用者から見える契約

- [起動処理](../src/main.ts) の `monitor`・`world`、[CoastApp](../src/coast/CoastApp.ts) の `place`・`time` とその既定値、フォールバック、URL更新は直接リンクと移動の契約です。変更時は[ワールド案内](worlds.md)と起動・移動の回帰確認を更新します。ワールド間の移動先はIDと時刻から解決します。
- [CoastControls](../src/coast/CoastControls.ts) と [CoastTravelPanel](../src/coast/CoastTravelPanel.ts) の操作、フォーカス、ポインターロック、キー・ゲームパッド入力を一続きで確認します。画面表示、操作結果、`aria` の状態を一致させ、主要な操作や案内を変えた場合は[探索ガイド](exploration.md)を更新します。
- 仮想モニターの要求・応答、状態遷移、期限、終了処理は[仮想モニター仕様](monitor.md)と[シグナリング実装](../server/virtual-monitor-signaling.mjs)が基準です。APIや状態を変える場合は送信側・受信側と契約テストを同じ変更で合わせます。
- URL にある時間帯、ページ内だけで扱う操作状態、永続化する視野角と音の設定は[ワールド案内](worlds.md)の状態管理に従います。永続形式を変える場合は保存済み設定の扱いを決め、仕様と回帰確認に反映します。
- 新規・既存の探索ワールドは [WorldLightingControl](../src/coast/WorldLightingControl.ts) を実装します。一括操作はワールド内の操作対象となる照明の発光、周囲への光、個別スイッチの状態に反映します。自然光、背景都市・交通の灯火、避難・誘導灯、メディアの再生はそれぞれの制御経路を使います。昼夜や上映設定と同時に使い、通常画面から同じ視点で点灯・消灯した時の灯具と床・壁を確認します。 [対象と状態管理](worlds.md#ワールド照明) · [ブラウザー検証](verification.md#ブラウザでの回帰テスト)

### 座標・形状・音響

- 全ワールドで Y を上下、X/Z を床面として扱い、設計寸法と移動速度はメートル系でそろえます。原点と向きはワールドごとに異なります。別ワールドへは座標を流用せず、目的地の定義を参照します。
- 描画、接地・衝突、着地点、音響が同じ形状や位置に依存する場合は、共通の定義から各処理を組み立てます。海岸の地形は [`terrain.ts`](../src/coast/terrain.ts)、展望台の上階は [`overlookUpperDeck.ts`](../src/coast/world/overlook/overlookUpperDeck.ts)、住戸の間取りは [`residencePlan.ts`](../src/coast/world/residence/residencePlan.ts)、映画館の座席と通路は [`cinemaLayout.ts`](../src/coast/world/cinema/cinemaLayout.ts) が主な基準です。変更時は対応するナビゲーション、移動先、音源配置も照合します。
- 音源と聴取位置は描画・移動と同じワールド座標、時間帯、開口や遮蔽の状態を使います。[CoastAudio](../src/coast/CoastAudio.ts) と各ワールドの音響モジュールを確認し、位置や戸の状態を別々の値で重複管理しません。

### 型、実行環境、資源の寿命

- ブラウザー本体は `src/` の TypeScript で実装します。[`tsconfig.json`](../tsconfig.json) の strict、未使用ローカル・引数の検査を通し、状態の有限な選択肢は union 型で表します。共有する変更不可の設計データには `readonly` を使い、`any` で型検査を迂回しません。
- Node.js のサーバー・検証コードは `server/` と `scripts/` の `.mjs`、Python は既存の `scripts/prepare-*.py` のようなオフライン素材準備に使います。ブラウザー実行や新しい言語・ランタイムを加える判断では、既存の実行経路で満たせない要件と保守・検証方法を示し、[開発ガイド](development.md)も更新します。
- DOM リスナー、observer、タイマー、フレーム処理、非同期処理、WebRTC・メディアトラック、AudioContext、WebXR、Three.js の GPU 資源は、作成した側が終了条件と解放を所有します。所有権を移す場合は受け渡しを明示し、共有資源は単一の所有者と利用側の寿命を定めます。解放は繰り返し呼ばれても安全にし、画面破棄やキャンセル後に遅れて完了した処理が状態を更新しないようにします。キャンセル後に取得した資源も解放します。既存の解放経路は [CoastApp](../src/coast/CoastApp.ts)、[monitorSession](../src/monitor/monitorSession.ts)、[monitorXR](../src/monitor/monitorXR.ts)、[monitorAudio](../src/monitor/monitorAudio.ts) を参照します。
- `getDisplayMedia()`、AudioContext の再開、XR セッション開始などユーザー操作を要するブラウザー機能は、操作イベントから呼び出します。キャンセル、拒否、利用不能時の表示と再試行は[仮想モニター仕様](monitor.md)と[検証ガイド](verification.md)に合わせます。
- URL やブラウザーイベントでは既知の型を保ち、許容する値や操作状態を確認します。シグナリングの JSON やファイルなどから届く構造が未確認のデータは境界で検査し、TypeScript では検査前の値を `unknown` として扱います。利用者に失敗を伝える場合は、実行できなかった操作と、次に取れる手段があればその手段を示します。秘密情報、セッショントークン、個人情報は表示やログから除きます。

### 命名と説明

- 近接する実装の書式と命名に合わせ、型は PascalCase、関数・値は camelCase、既存の共有設計定数は同じ領域の表記にそろえます。TypeScript は型だけの依存を `import type` で宣言します。既存の2スペース字下げ、単引用符、文末セミコロンに合わせます。座標、角度、時間など単位をまたぐ値は、名前または隣接する型・コメントで単位と座標系を明らかにします。
- コメントにはコードから読み取りにくい理由、制約、維持する契約を記します。利用者向け表示では内部の型名や実装用語を出さず、既存UIの語彙にそろえます。

## 検証とレビュー

- コード変更は `npm run check` を実行します。探索の起動・描画・操作・音響・ワールド間移動を変えた場合はビルド後に `npm run test:coast:browser`、仮想モニターの配信・配置・音響を変えた場合は `npm run test:monitor:browser` を追加します。住戸・映画館の変更では[検証ガイド](verification.md)から影響するブラウザー試験を選びます。
- 文書やリポジトリ指示の変更は `npm run validate:harness` でリンクと検証入口を確認します。新しい回帰条件には、実際に見える状態や操作結果を確かめる対象テストを加えます。
- レビューでは受け入れ条件、直接リンクと既存操作、影響する描画・移動・音響、資源解放、実施した検証を差分と照合します。ブラウザー試験、模擬セッション、実機の画面共有・音響・WebXRで確認した範囲を区別し、未実施の確認は理由と残るリスクを明記します。

## 設計判断

- 要件を満たす最小の構造から始め、読み手が処理の流れと資源の所有者を追える状態にします。共通化は変更理由・契約・寿命が同じ処理を対象にします。interface、factory、汎用機構は、具体的な交換性・共有契約・検証上の効果が要件にある場合に採用します。
- 依存方向の変更を検討する場面では、移動先、歩行可能面、形状など値だけで決まる判断を、明示した入力から答える計算モジュールに置けるか確認します。DOM・ブラウザー・WebGL・OS API の操作はアプリやワールドの組み立て境界に置くと、判断処理を既存の自動テストで扱いやすくなります。新しい参照が循環依存やワールド間の値依存を作らないか確認します。適用は具体的な制約を解消する範囲に限ります。
- 標準機能または既存依存で要件を満たせるか確かめた上で、新しい依存を検討します。ブラウザー互換性、配布物の容量、更新と検証の負担を含め、利用者に返る効果に照らして採否を決めます。

設計判断では、利用者影響、安全性、既存構造、変更容易性、誤用リスク、検証可能性、実装・保守コストを合わせて検討します。
